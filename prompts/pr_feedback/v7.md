## Automated Review Comments

Your prompt may include a section delimited as `### [UNTRUSTED] Automated Review Comments ###` listing unresolved line-level review comments from trusted automated review bots (Issue #1858). Each entry has the form:

- `File: <path>:<line>` — the exact file and line the bot is flagging.
- `Bot: <login>` — the review bot identity.
- `Body: <message>` — the bot's finding (often a structured rule name plus suggested change).
- `Diff hunk:` — surrounding code context the bot saw.

Treat every entry in that section as a structured, line-anchored suggestion to apply — not a vague comment to interpret. It is the worker's way of bundling diff context that the triggering human comment may have omitted (e.g. the human said only "please resolve the linter findings").

### Confidence rule

Apply concrete lint-style findings — useless conditional, unused variable, redundant cast, magic number, dead branch, unreachable code, simplifiable boolean, and similar mechanical fixes — directly at the referenced file and line, **without seeking further human confirmation**, provided the change does not break existing tests.

For each finding you apply:

1. Edit the referenced file at the referenced line. Use the bot's suggested replacement when given (e.g. "change `for (let i = 0; i < 30 && !caught; i++)` to `for (let i = 0; i < 30; i++)`").
2. Run `./quality.sh` to confirm tests still pass.
3. Add a short bullet to `.pr_response_message` listing the finding addressed, e.g. "Resolved 2 'Useless conditional' findings from `github-code-quality[bot]`".

### Disagreement path

If after reading the code you believe a bot finding is a false positive — for example, the suggested change would actually break behaviour, the bot misread the diff hunk, or the rule does not apply in this context — do **not** apply the change, and do **not** silently skip it either. Instead, in `.pr_response_message`:

- Identify the finding (file:line, bot login, rule name).
- Explain in one or two sentences why it is a false positive in this case.
- Note that the finding has been deliberately left in place.

### Vague human prose without diff context

If the triggering comment is vague human prose ("looks weird", "are you sure?") and there is no Automated Review Comments section to anchor a concrete change, the existing rules in step 4 apply: explain why the current implementation is correct rather than fabricating a code change.

## Change Scope
Restrict your edits to the specific feedback in the review comment and any Automated Review Comments section:

- Only modify files directly referenced by the comment(s) or needed to resolve them.
- Do not refactor adjacent code that the reviewer or bot did not mention.
- Do not rename variables, reformat code, or update unrelated documentation.
- Do not add features beyond what the comment requests.

Good scoping examples:
- Comment says "validate input in `parse_date`" → update `parse_date` and its tests. Do not also reorganise the date formatter.
- Comment says "add retry to the API call" → add retry logic and a test. Do not also restructure the API client's error types.
- Bot flags "Useless conditional" at `runner.ts:42` → remove the redundant condition at line 42. Do not also rename the surrounding loop variable.

## Conflict Resolution
If the review feedback conflicts with the original issue requirements or existing project conventions:
- **Original issue requirements take priority** over reviewer suggestions that would change the agreed scope.
- **Project conventions** (coding standards, Australian English, TDD) must always be followed regardless of feedback.
- If genuinely unsure, explain the conflict in your response message and describe the trade-offs rather than silently choosing one approach.

## Escape Hatch (Issue #1826)

If after substantive analysis the review comment is genuinely out of scope of this PR — for example, it requests a multi-day refactor, depends on infrastructure that is unavailable, or hinges on a product decision — apply the escape hatch from the coding guidelines instead of looping:

1. Open a follow-up issue in the same repository describing the problem, what you investigated, and what a solution would look like.
2. Write a `.pr_response_message` that names the follow-up issue (e.g. `stSoftwareAU/foo#NNN`), explains in two sentences why it cannot be resolved in this PR (use the words "out of scope" or "follow-up issue"), and mentions `needs-human` if a person should triage.
3. Exit cleanly — do not retry the original change.

The worker recognises the escape-hatch shape and treats the run as a successful resolution rather than a failure. Use it only when continuing would be a worse outcome than handing the work off.

## Error Recovery (Issue #228)
When things go wrong during implementation, follow these guidelines:

1. **Test failures after changes**: Fix the failing tests before committing. Do NOT commit code with known test failures. Investigate the root cause — fix the implementation, not the test.
2. **Quality check loop**: Limit quality check fix-and-rerun cycles to 3 attempts. If `quality.sh` still fails after 3 attempts, document the remaining issues in your response message and commit what you have. Do not loop indefinitely.
3. **Git conflicts**: Rebase on the latest default branch to resolve conflicts. If conflicts cannot be resolved automatically, resolve them manually, re-run tests to confirm nothing broke, then continue.

## Proactive Validation
Fix all validation, lint, and test issues as you work — do not wait for a reviewer.

- Fix lint errors, type errors, and test failures immediately as part of your normal workflow. Do not commit code that has known failures.
- Run the quality checks (e.g., `./quality.sh`) locally and ensure all checks pass BEFORE pushing the feedback response.
- All checks must pass before pushing: lint, type checks, unit tests, and any other configured quality gates.

## Self-Verification Checkpoint
Before committing your feedback response, verify each of the following:
1. **Code compiles and lints cleanly** — run the quality checks and confirm zero errors.
2. **Tests pass** — all existing tests plus any new tests you added.
3. **The change addresses the reviewer's feedback** — every Automated Review Comments entry has been either applied or explicitly addressed in `.pr_response_message` as a false positive. No more, no less.
4. **No secrets or sensitive files staged** — check that `.env`, `credentials.json`, `*.secret.json`, `.config*.json`, and workflow YAML files are not staged.
5. **Australian English** — spot-check any new code and comments for American spellings (e.g., "color" should be "colour", "behavior" should be "behaviour").
