### Step 1 — Attack the draft

Adversarially critique the draft plan shown above. Ask **"what's wrong with this approach?"** and be specific and harsh. Consider at least:

- **Missing work** — asks in the issue with no sub-issue covering them; tests, docs, migrations, or rollout steps omitted.
- **Mis-scoping** — sub-issues too large for a single ~500-line PR, or so small they should be merged; tasks spanning unrelated modules.
- **Dependencies** — wrong, missing, or circular `Depends on #N` links; work ordered so it cannot compile or test.
- **Over-engineering** — speculative sub-issues, premature abstraction, or scope the issue never asked for (KISS).
- **Duplication** — sub-issues that recreate an existing open issue you listed earlier.
- **Weak acceptance criteria** — criteria that are not specific or testable.
- **A simpler alternative** — a materially simpler plan that still satisfies the issue.

#### Verify each `## Failure Detection` section before you publish it (Issue #3273)

A deterministic post-publish gate rejects any sub-issue whose `## Failure Detection` section is missing, empty, or still the bracketed template placeholder — so a section you drop between draft and publish becomes a stranded, failed planning run. Prevent that: immediately before running `gh issue create` for **each** sub-issue, re-read the **final** body you are about to publish and confirm its `## Failure Detection` section is filled. The section is filled only when it carries one of:

- a concrete failure-detection criterion — an automated test, a CI quality gate, or a post-release alert naming how and where a regression in this work is detected (a console log alone never qualifies); or
- an explicit `N/A — <reason>` line for docs-only or prompt-only work with no runtime failure surface.

A bare bracketed placeholder such as `[...]` does **not** count as filled. The heading may be a `## Failure Detection` section or a bolded `**Failure detection:**` line — either shape is accepted, matching the gate.

If a sub-issue's `## Failure Detection` section is missing, empty, or still a bracketed placeholder, **repair your own draft** — fill in the real criterion (or the `N/A — <reason>`) — before you publish it. If you genuinely cannot state a real failure-detection criterion for a sub-issue, treat that as a blocker to publishing **that** sub-issue: re-scope, merge, or drop it rather than publishing a non-conforming sub-issue and leaving the gate to catch it after the fact.

### When the revised plan needs zero sub-issues (Issue #2994)

If your revision concludes the issue is simple enough that it needs **zero** sub-issues, you must not silently close the parent — that would lose the work, because no implementing PR is ever raised. Decide which of these two cases applies:

- **There is still real work to do** (the issue describes a genuine change, just small enough that breaking it into multiple sub-issues adds no value). This is the **default** for any zero-sub-issue outcome. You **must** create exactly **one** carrier sub-issue that captures the remaining work, before closing the parent:
  - Label it exactly the way you label sibling sub-issues in Step 3 (a descriptive `bug` or `enhancement`, never a reserved workflow label) so the worker's new-work scan claims and implements it — an unlabelled carrier would never be picked up and would reproduce the bug.
  - Its body must include `Part of #{{ISSUE_NUMBER}}` and testable acceptance criteria, exactly like any other sub-issue. Apply the same `## Failure Detection` verification from Step 3 to the carrier before you publish it.

  ```bash
  gh issue create --repo {{REPO}} --title "Carrier title — implement <the remaining work>" --body "Description of the remaining work.

  Part of #{{ISSUE_NUMBER}}" --label "enhancement"
  ```

- **There is genuinely nothing to implement** — the issue is invalid, a duplicate, or already implemented. Only then may you close the parent with **zero** sub-issues and **no** carrier. To take this path you **must** make the signal explicit in your summary comment: include a line of the exact form `Nothing to do — <reason>` (for example `Nothing to do — already implemented in #1234`) **and** apply the matching descriptive label (`invalid`, `duplicate`, or `wontfix`) to the parent. Without that explicit signal, treat the close as the default case above and create a carrier.

This is the **only** exception. Never close a zero-sub-issue parent with no carrier when real work remains.
