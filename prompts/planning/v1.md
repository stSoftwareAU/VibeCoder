## Planning Mode (Issue #275)

You are in **planning mode**. Your task is to break down the issue into actionable sub-issues
and work packages — NOT to implement any code changes.

### CRITICAL CONSTRAINTS:
1. Do **NOT** create any branches, commits, or pull requests
2. Do **NOT** modify any code files
3. Do **NOT** implement any fixes or features
4. You MUST only create GitHub issues as sub-tasks

### Your Task

Analyse the issue and create a set of GitHub sub-issues that break the work down into
meaningful, implementable tasks. Each sub-issue should be:

- **Self-contained**: Can be worked on independently
- **Clearly scoped**: Has a specific, well-defined outcome
- **Appropriately sized**: Not too large (can be completed in a single PR) and not too small (trivial one-line changes can be grouped)
- **Ordered**: Created in a logical implementation order where dependencies are clear

### Sub-Issue Requirements

For each sub-issue you create:
1. **Title**: Clear, concise description of the task
2. **Description**: Include:
   - What needs to be done
   - Acceptance criteria (how to verify the task is complete)
   - Any dependencies on other sub-issues
   - Relevant context from the parent issue
3. **Labels**: Add the repository's configured issue labels (e.g., `claude`, `help wanted`) so the Vibe Coder can pick them up
4. **Reference**: Link back to the parent issue with "Part of #{{ISSUE_NUMBER}}"

### Planning Guidelines

{{CODING_GUIDELINES}}

- Use Australian English spelling (e.g., colour, behaviour, organisation)
- Consider test-driven development: include testing requirements in each sub-issue
- Group related changes together (e.g., "Add X model and its tests" rather than separate issues for model and tests)
- If the issue mentions specific technologies or approaches, reflect those in the sub-issues
- If the scope is unclear, create fewer, broader sub-issues rather than many speculative ones

### Output

Use the `gh` CLI to create sub-issues in the repository. For example:
```bash
gh issue create --repo OWNER/REPO --title "Sub-task title" --body "Description" --label "claude" --label "help wanted"
```

After creating all sub-issues, post a summary comment on the parent issue listing:
- The sub-issues created (with links)
- The suggested implementation order
- Any assumptions or decisions made during planning

Then remove the `{{PLANNING_LABEL}}` label from the parent issue to signal that planning is complete.
