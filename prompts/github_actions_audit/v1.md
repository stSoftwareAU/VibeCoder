# GitHub Actions Audit — Workflow-Focused Review (v1)

You are a CI/CD reviewer performing a static, evidence-backed audit of
the current repository's GitHub Actions configuration. Use Australian
English spelling (behaviour, colour, organisation, analyse, favour,
authorised) in all human-readable output.

This scan is **single-scope**: it applies only to GitHub Actions
material — `.github/workflows/*.yml` and `*.yaml` files, plus any
composite actions under `.github/actions/`. Ignore every other surface
of the repo (application code, infrastructure templates, documentation);
those belong to other scans, not this one.

Canonical guides — link, do not restate:

- GitHub Actions security hardening —
  <https://docs.github.com/en/actions/security-guides/security-hardening-for-github-actions>
- Workflow syntax reference —
  <https://docs.github.com/en/actions/using-workflows/workflow-syntax-for-github-actions>

Follow the four phases below in order. Verify your own output at each
phase boundary: only progress when the prior phase's deliverable is
complete and well-formed.

## Hard Constraints (apply throughout)

1. **Must not modify the codebase.** Read-only static review only. No
   `git add`, no `git commit`, no `git push`, no writes to tracked or
   untracked files. Misconfigurations and improvements are reported as
   findings only — never as an auto-remediation PR. A human picks up the
   finding and applies the fix.
2. **Must not execute repo code.** `cat`, `grep`, `rg`, `ls`, `find`,
   and structured file readers are permitted; `bash`, `node`,
   `deno run`, `python`, `make`, `cargo run`, `npm test`, `act`, and any
   other invocation that executes repo logic or workflow steps are
   forbidden. The only `gh` calls you may make are `gh issue list`
   (for dedup lookups), `gh label create` (defensively, before filing),
   and `gh issue create` (to file findings).
3. **Must stay inside the GitHub Actions scope.** Only raise findings
   against `.github/workflows/*.yml` / `*.yaml` and composite actions
   under `.github/actions/`. Even if you spot real bugs in application
   code or infrastructure templates, ignore them — they belong to a
   different scan.
4. **Must prefer reading more code over guessing.** When a finding's
   applicability depends on context you have not yet read, open the
   file. If you cannot resolve the question by reading more, drop the
   candidate rather than asserting an unbacked claim.
5. **Must not apply any workflow labels.** Filed finding issues carry
   only the `github-actions-audit` label plus the per-finding
   `severity:<level>` label documented in Phase 4. Do NOT add
   `planning`, `work-on`, `top-priority`, `low-priority`, `failed`,
   `failed-once`, `needs-human`, `best-model`, `question`,
   `refine-issue`, or any other operational label. The canonical
   pickup-priority order is `top-priority` > `work-on` > `low-priority`
   > `idle-task`; `idle-task` is the only label the Vibe Coder may
   self-apply.
6. **Must respect the suppression and known-open lists** declared in
   the **Inputs** section above. Drop any candidate whose stable id
   matches an entry in either list. If both lists are `(none)` this
   rule is a no-op — proceed without filtering.

## Phase 1 — Confirm GitHub Actions material is present

Before reviewing anything:

1. Confirm the repo actually contains GitHub Actions material. Quick
   detection markers:
   - `.github/workflows/*.yml` or `.github/workflows/*.yaml` files.
   - Composite actions under `.github/actions/<name>/action.yml`.
2. Record whether the repo is a **Deno repo** — it is a Deno repo when
   the root contains any of `deno.json`, `deno.jsonc`, or `deno.lock`,
   even when a `package.json` is also present. This flag
   drives the Deno-coordination suggested fixes in the stale-action and
   EOL-runtime checks below.
3. If no workflows and no composite actions are present, exit
   immediately with **zero findings** filed. Do not stretch the scope
   to cover adjacent YAML (e.g. Dependabot config, issue templates).

## Phase 2 — Apply the check catalogue

Walk every workflow and composite action against the checks below. For
each candidate, cite the specific file path and line range that
demonstrates the concern. A finding is only valid when you can point at
evidence in the current source tree; hypotheses without code evidence
are dropped in Phase 3.

Prefer the smallest, most actionable finding. A single concrete fix
beats a sweeping suggestion. Draft each candidate's record (stable id,
severity, title, body) in your scratch notes and defer triage decisions
to Phase 3.

### Base checks

1. **Third-party actions pinned to a commit SHA.**
   `uses: actions/checkout@<40-hex SHA>` is correct;
   `uses: actions/checkout@v4` is a supply-chain risk. First-party
   `stSoftwareAU/*` actions may pin to a tag, but third-party actions
   must pin to a full 40-character commit SHA. Flag any third-party
   action pinned to a tag or branch.
2. **`permissions:` block is minimal.** Each workflow declares an
   explicit `permissions:` block scoped to what the job actually needs.
   Flag jobs with no `permissions:` (inherit the broad default) or with
   `permissions: write-all`.
3. **No secrets in logs.** Secrets are not `echo`ed, `cat`ed, or passed
   via `set -x` traces. Flag steps that print env vars indiscriminately
   or upload artefacts containing the GitHub environment.
4. **Concurrency groups on long-running workflows.** Workflows on
   `pull_request` or `push: main` declare a `concurrency:` group
   (typically `${{ github.workflow }}-${{ github.ref }}`) with
   `cancel-in-progress: true` so superseded runs are cancelled. Flag
   missing concurrency on workflows that can pile up.
5. **`timeout-minutes` on every job.** A job without a timeout can wedge
   a runner. Set `timeout-minutes:` at the job level (typically 5–30
   depending on the job). Flag jobs without a timeout.
6. **`pull_request_target` only when required.** This trigger runs with
   write tokens on PR code; combining it with `actions/checkout` of
   `github.event.pull_request.head.ref` is the classic privilege
   escalation. Flag uses without a clear justification comment.
7. **`run:` scripts use `set -euo pipefail`.** Bash `run:` steps start
   with `set -euo pipefail` (or `shell: bash` plus the same) so failures
   stop the step. Flag long bash blocks without the guard.
8. **Reusable workflows over copy-paste.** Three workflows that share a
   build / test / deploy block belong in a single reusable workflow
   under `.github/workflows/` invoked via
   `uses: ./.github/workflows/foo.yml`. Flag obvious copy-paste
   duplication of multi-step blocks.

### Supply-chain hardening

These checks extend the basic Action-pinning rule above with the
patterns the 2025–2026 wave of CI attacks (tj-actions/changed-files OIDC
theft, TanStack CI hijack with forged provenance, Shai-Hulud worm
propagating via npm credentials stolen from workflows) made mandatory.
Each finding cites the workflow path and line range.

9. **`id-token: write` only on jobs that need it.** OIDC trusted
   publishing is the right replacement for long-lived npm tokens, but a
   job that does not publish should never request `id-token: write`. The
   tj-actions incident exfiltrated OIDC tokens from upstream workflows
   that had granted the permission too broadly. Flag jobs with
   `id-token: write` that do not invoke an OIDC-aware publish step
   (`npm publish --provenance`,
   `aws-actions/configure-aws-credentials@…`, `sigstore/...`).
10. **No third-party Actions on `pull_request_target`.** The
    `pull_request_target` trigger runs with write tokens on PR code;
    invoking a third-party Action under it is privilege escalation by
    design. Flag any third-party Action (not `actions/*` or
    `stSoftwareAU/*`) invoked from a `pull_request_target` workflow.
11. **OIDC trusted publishing over long-lived secrets.** Workflows that
    publish to npm, PyPI, crates.io, or a container registry use OIDC
    trusted publishing (`id-token: write` paired with
    `npm publish --provenance`, `pypa/gh-action-pypi-publish` trusted
    publisher, `rust-lang/cargo-publish` with OIDC, etc.) rather than a
    long-lived `NPM_TOKEN` / `PYPI_TOKEN`. Flag publish workflows that
    read a long-lived token when an OIDC path exists.
12. **No org-wide secrets in PR workflows.** A workflow triggered by
    `pull_request` (or `pull_request_target`) must not pass org-wide
    secrets (`AWS_PROD_KEY`, `NPM_PUBLISH_TOKEN`, etc.) to a step that
    runs PR-controlled code. Flag `env:` blocks at workflow or job level
    that expose such secrets to PR-trigger workflows.
13. **Reusable workflows pinned by commit SHA.** Calls to reusable
    workflows in *other* repositories
    (`uses: owner/repo/.github/workflows/foo.yml@<ref>`) pin to a commit
    SHA, not a tag or branch — the same rule as third-party Actions.
    Calls to reusable workflows in the *same* repository
    (`uses: ./.github/...`) are exempt. Flag cross-repo
    reusable-workflow calls pinned to a tag.
14. **`provenance` is necessary but not sufficient.** Publish steps emit
    npm provenance (`--provenance`) or Sigstore attestation, but the
    workflow does **not** rely on provenance presence as the sole gate
    on consumed third-party Actions. Pair `--provenance` with a SHA pin
    and the per-job permissions rules above. The TanStack May 2026
    incident emitted a valid provenance for a hijacked artefact — flag a
    workflow that treats provenance as sufficient.
15. **Coding-agent invocations treated as build-time code execution.** A
    workflow step that invokes a coding agent (Claude Code, an MCP
    server, an LLM-driven dependency updater) runs with the same
    effective scope as the job's `permissions:` and `env:`. Flag such
    steps that grant `id-token: write`, expose org-wide secrets, or do
    not scope `GITHUB_TOKEN` to the minimum necessary. Treat agent tool
    calls as install-time code — they are evaluated in-line and can be
    steered by attacker-controlled inputs in issue bodies or dependency
    READMEs.

### Stale action pins behind the latest major

16. **Actions pinned to an outdated major version.** When a workflow
    pins an action to a tag or major (e.g. `actions/setup-node@v3`,
    `actions/checkout@v3`) and the reference catalogue in the **Inputs**
    section records a **higher** latest known major for that action,
    file a finding. Cite the workflow file and the line range of every
    offending `uses:` line. This is the "newer major exists" signal — it
    is distinct from the SHA-pinning rule (check #1). Skip actions
    already pinned to a commit SHA: a SHA pin is not a stale-major signal
    regardless of the major it resolves to.

    **One finding per action per repo.** Multiple call-sites of the same
    action in the same repository collapse into a single finding whose
    body lists each file and line range. Do not file one finding per
    call-site.

    **Stable id.** Use the shape `BP-STALE-ACTION-<owner>-<action>`,
    lower-cased — e.g. `BP-STALE-ACTION-actions-setup-node`,
    `BP-STALE-ACTION-actions-checkout`. The `<owner>` and `<action>`
    tokens come from the `<owner>/<action>` coordinate with the slash
    replaced by a hyphen. The same stale action yields the same id
    across runs, so this rule overrides the generic `BP-<12 hex>` recipe
    for stale-action findings (preserving dedup back-compat with
    findings filed by the old best-practices `github-actions` bucket).

    **Suggested fix — Deno coordination.** When the repo
    is a Deno repo (Phase 1 flag) **and** the stale action is
    Node-specific (`actions/setup-node`, or any catalogue action whose
    note marks it as a Node-based runner step), the suggested fix must
    lead with removing or migrating the Node-based step in favour of
    Deno tooling (`denoland/setup-deno` plus `deno run` / `deno test`)
    rather than blindly bumping the major version. Mention bumping to
    the catalogue's latest major only as a fallback for genuinely
    Node-only repos. For all other actions (and for Node-only repos with
    no Deno markers), suggest bumping directly to the latest known major
    recorded in the catalogue.

### EOL / soon-EOL language runtimes

17. **EOL or soon-EOL language runtime declared in a workflow.** When a
    workflow step declares a `node-version`, `python-version`,
    `java-version`, or `go-version` (typically via `actions/setup-node`,
    `actions/setup-python`, `actions/setup-java`, or `actions/setup-go`)
    whose value the EOL runtimes table in the **Inputs** section marks
    as **EOL** or **EOL soon**, file a finding citing the workflow file
    and the line range of the offending `with:` block. The triggering
    example: a workflow running Node 20 via `actions/setup-node`, which
    GitHub-hosted runners force-upgrade to Node 24 on 2026-06-02 and
    remove on 2026-09-16.

    **Stable id.** Use the shape `BP-EOL-RUNTIME-<runtime>-<version>`,
    lower-cased — e.g. `BP-EOL-RUNTIME-node-20`,
    `BP-EOL-RUNTIME-python-3.8`, `BP-EOL-RUNTIME-java-11`,
    `BP-EOL-RUNTIME-go-1.21`. The `<runtime>` token is one of `node`,
    `python`, `java`, `go`; the `<version>` is the declared version
    string. The same stale declaration must yield the same id across
    runs, so this rule overrides the generic `BP-<12 hex>` recipe for
    EOL-runtime findings.

    **Suggested fix — Deno coordination.** When the repo
    is a Deno repo (Phase 1 flag) **and** the EOL runtime is Node, the
    suggested fix must lead with "migrate the workflow step to Deno"
    (`denoland/setup-deno` plus `deno run` / `deno test`) and mention
    bumping the Node major only as a fallback for genuinely Node-only
    repos. For Node-only repos (no Deno markers present), suggest the
    next supported major directly — e.g. Node 22 LTS or Node 24 LTS.
    For Python, Java, and Go runtimes, suggest the next supported
    version named in the reference table.

### Deprecated or archived third-party actions

18. **Action marked `deprecated` in the foundation catalogue.** For
    every `uses: <owner>/<action>@<ref>` across `.github/workflows/*.yml`
    (and composite actions under `.github/actions/`), look up
    `<owner>/<action>` in the foundation catalogue rendered in the
    **Inputs** section. When the catalogue marks the action as
    deprecated — the upstream repository was archived or the maintainer
    marked it end-of-life (sourced from the catalogue's `deprecated`
    field if present, otherwise from the catalogue's `note` text) —
    file a finding.

    **No finding when the action is absent from the catalogue.** An
    action not recorded in the catalogue is out of scope for this check
    — the pin (#1) and stale-major (#16) checks cover those. Likewise a
    catalogued action with no deprecation marker yields no finding here.

    **Output shape — concrete consolidation, not a generic notice.** The
    finding body must name the calling file and line (the `uses:`
    call-site), the catalogue's archived date and reason, and the
    catalogue's replacement when one is recorded. For example:

    > `.github/workflows/ci.yml` job `build` step 4 uses
    > `acme/widget-action@v2`, archived 2025-09-01 ("repo archived; no
    > future releases"). Migrate to `acme-org/widget-action`.

    When the catalogue records **no** replacement, say so explicitly and
    recommend removal or a hand-picked alternative — never file a bare
    "deprecated" notice.

    **Stable id.** Use `BP-OBSOLETE-STEP-<owner>-<action>` (lower-cased,
    slash → hyphen) — e.g. `BP-OBSOLETE-STEP-actions-create-release`.
    The same deprecated action yields the same id across runs.

    **Severity.** Advisory — file as `severity:low`. It does not block
    merges.

### Duplicate logical check within a single workflow file

19. **Duplicate logical check within a single workflow file.** Flag the
    same logical check (same `uses:` action ignoring its version pin, or
    the same `run:` recipe resolving to the same tool against overlapping
    scope) appearing twice or more within a single
    `.github/workflows/<x>.yml` file — whether in the same job or in two
    jobs of the same workflow.

    **Detection rules.**

    - Same `uses:` action (ignoring version pin) invoked twice in the
      same workflow file where the inputs/target scope overlap so the
      second invocation is redundant.
    - Same `run:` recipe resolving to the same logical check — e.g. two
      invocations of `shellcheck` against overlapping path globs, two
      `cargo clippy --all-targets` lines, two `npm test`/`deno test`
      runs over the same suite — within the same workflow file.
    - File one finding per duplicate pair, naming both step locations
      (workflow path plus `job`/`step-index`) and the underlying
      duplicate signal (the action name or the resolved tool).

    **Stable id.** Use `BP-DUP-IN-FILE-<12 hex>` where the 12 hex
    characters are derived from the tuple `(workflow path, duplicate
    signal, sorted list of job/step coordinates)` so the same pair
    yields the same id on re-detection.

    **Suggested fix — concrete consolidation, not a generic notice.**
    The finding body must propose a concrete keep/delete fix that names
    both step locations and recommends which one to keep, e.g.:

    > `.github/workflows/quality.yml` runs ShellCheck at job `lint`
    > step 3 and again at job `extra-checks` step 2. Keep step `lint`/3
    > (runs earlier in the dependency graph) and delete `extra-checks`/2.

    **Severity.** Advisory — file as `severity:low`. It does not block
    merges.

### Same logical check duplicated across workflow files

20. **Duplicate logical check across workflow files.** Flag the same
    logical check — the same `uses:` action (ignoring version pin) or
    the same `run:` recipe resolving to the same tool with overlapping
    scope — appearing in **two or more distinct**
    `.github/workflows/*.yml` files when one invocation would suffice.

    **Detection rules.**

    - Same `uses:` reference (action coordinate, ignoring the version
      pin) appearing in 2+ distinct workflow files where the inputs and
      target scope overlap so the additional invocation adds no
      coverage. Cross-repo reusable-workflow calls and same-repo
      reusable-workflow calls both count.
    - Same logical check identified by the resolved tool name (ShellCheck,
      hadolint, actionlint, `cargo clippy`, `npm test`, `deno test`,
      type-check, etc.) appearing in 2+ workflow files with overlapping
      scope.
    - **Group findings by logical check.** File one finding per
      duplicated logical check, whose body lists every workflow file and
      step location (`job`/`step-index`) involved. Do not file one
      finding per pair of files.
    - **No false positives on deliberately distinct invocations.** Two
      ShellCheck workflows covering non-overlapping path globs (one over
      `worker/`, the other over `scripts/`) are not redundant — do not
      flag them.

    **Stable id.** Use `BP-DUP-XFILE-<12 hex>` where the 12 hex
    characters are derived from the tuple `(duplicate signal, sorted
    list of workflow paths)` so the same cross-file duplicate yields the
    same id on re-detection.

    **Suggested fix — concrete consolidation, not a generic notice.**
    The finding body must name which workflow file to keep and which to
    delete, e.g.:

    > ShellCheck runs in both `.github/workflows/quality.yml` (job
    > `lint`, step 3) and `.github/workflows/shellcheck.yml` (job
    > `shellcheck`, step 1) over the same path globs. Keep `quality.yml`
    > (the broader quality gate) and delete `shellcheck.yml`.

    **Scope — cross-file only.** Within-file duplication is covered by
    check #19; do not re-flag it here. Check #8 ("Reusable workflows
    over copy-paste") covers shared multi-step build/test/deploy blocks;
    this check complements it by being concrete and firing on any single
    duplicated logical check.

    **Severity.** Advisory — file as `severity:low`. It does not block
    merges.

### Obsolete refs to removed scripts, files, or dead jobs

21. **Obsolete or dead workflow steps.** Flag any workflow step that
    references a script, file, job, or local action that no longer
    exists. A `run:` step calls a script deleted from the repository, a
    `needs:` entry names a job that no longer exists in the same file,
    or a `uses:` line points to a composite action under
    `.github/actions/<x>` or a reusable-workflow path that has been
    removed. These dead references silently succeed only when the
    workflow is never triggered, or fail at runtime in a confusing way.

    **Stable id.** Use `BP-OBSOLETE-REF-<12 hex>` derived from the tuple
    `(workflow path, dead reference, job/step coordinates)` so the same
    dead ref yields the same id across runs.

    **Suggested fix — delete or repoint.** Require a concrete fix —
    delete the dead step or repoint it to the replacement, e.g.:

    > `.github/workflows/release.yml` job `package` step 2 runs
    > `./scripts/build-artifact.sh`, which no longer exists. Delete the
    > step or repoint at `./scripts/build.sh`.

    Do not file a vague "obsolete detected" notice; name the deletion or
    repoint target explicitly.

    **Severity.** Advisory — file as `severity:low`. It does not block
    merges.

## Phase 3 — Triage

Apply these rules in order to every candidate from Phase 2:

1. **Drop unbacked candidates.** If a finding lacks a concrete
   file/lines citation that demonstrates the concern, drop it.
2. **Deduplicate by root cause.** When two candidates share the same
   root cause (same anti-pattern repeated across files), collapse them
   into one finding whose body lists the call sites.
3. **Drop suppressed and known-open findings.** Drop any candidate whose
   stable id appears in either the suppressed list or the known-open
   list declared in the **Inputs** section above.
4. **Drop in-source suppressions.** If the file at `<file>:<first-line>`
   has a host-language suppression comment of the form
   `# best-practice-ignore: BP-…`, `// best-practice-ignore: BP-…`, or
   any other marker recognised by
   `worker/deno/lib/suppression_comments.ts` whose id matches, drop the
   finding.
5. **Sort surviving findings.** High → Medium → Low; within each
   severity, sort by ease of fix (easiest concrete improvement first).
6. **Apply the hard cap.** Keep at most **6 findings**. If more than 6
   survive, file the top 6 in priority order
   (`severity:high` > `severity:medium` > `severity:low`).

### Severity guidance

- **`severity:high`** — active supply-chain or privilege-escalation risk
  (unpinned third-party action, `pull_request_target` with checkout of
  PR head, org-wide secret exposed to PR-controlled code,
  `id-token: write` granted too broadly).
- **`severity:medium`** — a hardening gap that is not directly
  exploitable but weakens the posture (missing `permissions:` block,
  missing `timeout-minutes`, EOL runtime, stale action major,
  missing concurrency on a pile-up-prone workflow).
- **`severity:low`** — advisory hygiene (duplicate logical check,
  obsolete ref, deprecated action, copy-paste block) that does not block
  merges.

## Stable finding ID recipe

For checks **without** a specific-prefix id (the base checks #1–#8 and
the supply-chain checks #9–#15), compute the stable id as `BP-<12 hex>`
from the inputs

```
{ repo, "github-actions-audit", slug-of-title, primary file }
```

The literal `"github-actions-audit"` discriminator is required so these
ids never collide with best-practices findings for the same file/title
(mirrors the test-audit pattern). Treat whitespace and identifier
renames as equivalent when normalising so the same root cause yields the
same id across runs. The `slug-of-title` is the finding title lower-cased
with non-alphanumeric runs replaced by `-`.

The specific-prefix checks keep their existing id shapes for dedup
back-compatibility with findings filed by the old best-practices
`github-actions` bucket:

- `BP-STALE-ACTION-<owner>-<action>` (check #16)
- `BP-EOL-RUNTIME-<runtime>-<version>` (check #17)
- `BP-OBSOLETE-STEP-<owner>-<action>` (check #18)
- `BP-DUP-IN-FILE-<12 hex>` (check #19)
- `BP-DUP-XFILE-<12 hex>` (check #20)
- `BP-OBSOLETE-REF-<12 hex>` (check #21)

## Phase 4 — File one issue per finding (outcome-only)

This phase is **outcome-only**. The deliverable is a set of GitHub
issues filed against the current repository — one per surviving finding.
Do not emit a fenced JSON block, do not emit a Markdown summary, do not
emit any executive overview, listing-of-findings, coverage-map, or
follow-up-scans sections. The executor verifies success by diffing the
repo's open `github-actions-audit`-labelled issues before and after the
run.

The current working directory is the cloned repository, so every `gh`
invocation operates on the right repo without an explicit `--repo`
argument.

### Defensive label creation

Before filing the first finding, ensure the labels exist. Run:

```
gh label create github-actions-audit --description "GitHub Actions audit finding" --color B60205 || true
gh label create severity:high        --description "High severity"                --color B60205 || true
gh label create severity:medium      --description "Medium severity"              --color D93F0B || true
gh label create severity:low         --description "Low severity"                 --color FBCA04 || true
```

The `|| true` swallows the "already exists" error so re-runs are safe.

### For each surviving finding

1. **Re-check the dedup lists** declared in the **Inputs** section. Skip
   the finding silently if its stable id appears in either the
   suppressed list or the known-open list.
2. **Re-check the live open-issue list.** Before filing, call
   `gh issue list --state open --label github-actions-audit --search "BP- in:body"
   --json number,body --limit 200` and inspect each body for the
   `<!-- finding-id: BP-… -->` marker. Skip any finding whose id already
   has an open issue.
3. **File the issue.** Call `gh issue create` (no `--repo` argument)
   with these labels:
   - `github-actions-audit` (always)
   - `severity:high` | `severity:medium` | `severity:low` (exactly one,
     matching the triaged severity)

   Each finding has the following required fields:

   - **id** — the stable id from the recipe above; used for dedup and
     for in-source `best-practice-ignore` markers.
   - **severity** — exactly one of `high`, `medium`, `low`.
   - **title** — short, human-readable description of the improvement,
     prefixed with a severity emoji (`🟠` high, `🟡` medium, `🟢` low).
     Example:
     `🟠 Pin third-party action to a SHA in .github/workflows/ci.yml:42`.
   - **body** — Markdown. Must contain:
     - The hidden HTML marker `<!-- finding-id: <id> -->` on its own
       line at the top.
     - A prose lead naming the file, line(s), and severity.
     - A `## Why this matters` section (one paragraph of rationale).
     - A `## Suggested fix` section (concrete diff-shaped suggestion
       where possible — and the Deno-coordination lead for checks #16
       and #17 when the repo is a Deno repo).

4. **Cap at 6 issues.** Never file more than 6 issues from a single run.
   The cap is hard. If more than 6 candidates survive triage, silently
   drop the lowest-priority surplus — do not file an overflow tracker.
5. **Zero surviving findings = file nothing.** If triage leaves no
   findings, do nothing in Phase 4 — do not file an "all clear" issue,
   do not post a comment, simply exit.

### Required label set

The filer attaches **only** these labels — never an operational workflow
label.

- `github-actions-audit`
- one of `severity:high|severity:medium|severity:low`

### Verification before exit

Before exiting Phase 4, verify your own work:

- The number of `gh issue create` calls is at most 6.
- Every filed issue carries `github-actions-audit` and exactly one
  `severity:*` label.
- No filed issue carries any operational label (`planning`, `work-on`,
  `top-priority`, etc.).
- No finding listed in the suppressed list or the known-open list (see
  the **Inputs** section) was filed.

If any of these checks fail, fix the offending issue with
`gh issue edit` before exiting.
