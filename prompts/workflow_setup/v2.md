   branch name to configure triggers, paths, and tool versions correctly.
2. **Trigger on relevant events only** — use `pull_request` for quality checks,
   `schedule` for periodic security scans, and `push` to the default branch

3. **Use the default branch name** — reference `{{DEFAULT_BRANCH}}` in branch
   filters rather than hard-coding `main` or `master`.
4. **Avoid conflicts** — check the existing workflows summary above and ensure
   generated workflows do not duplicate checks already in place.
5. **Group related checks** — where sensible, combine related checks into a
   single workflow file (e.g., lint + format in one quality workflow) to
   minimise CI overhead. Do not force unrelated checks together.
6. **Include clear comments** — add YAML comments explaining each step so

7. **Follow best practices** — use pinned action versions (e.g.,
   `actions/checkout@v4`), set appropriate timeouts, and use least-privilege

8. **Use Australian English** in all comments and descriptions (e.g., behaviour,
   colour, organisation, analyse, minimise).

### CI Hardening Defaults

These defaults codify lessons learnt from production CI work on sibling
repositories (private-repo-22 issues #18–#24). Apply them to every workflow you
generate unless a guideline below explicitly says otherwise.

1. **Pin actions to fully-qualified versions.** First-party actions such as
   `actions/checkout`, `actions/setup-node`, and `actions/cache` must be pinned
   to a major-version tag (e.g., `actions/checkout@v4`, `actions/setup-node@v4`).
   For third-party actions used in security-sensitive workflows (gitleaks,
   trivy, codeql-action variants, release tooling), prefer SHA pinning with the
   tag noted in a trailing comment, e.g.
   `gitleaks/gitleaks-action@<sha> # v8.x`.
2. **Use workspace-relative checkout paths.** Never check out into a
   `../sibling` path — it escapes the runner workspace and breaks subsequent
   actions that assume `${{ github.workspace }}`. If a sibling repository must
   be cloned alongside the primary checkout, use the `path:` input to land it
   inside the workspace, e.g. `path: external/private-repo-16`.
3. **Scope security scans to the PR diff where supported.** When a tool
   accepts a commit range, run it against `origin/${{ github.base_ref }}..HEAD`
   on `pull_request` events instead of scanning the full history every run.
   For example, `gitleaks detect --log-opts="origin/${{ github.base_ref }}..HEAD"`.
   Pin the underlying CLI binary to a known version and record that version in
   a YAML comment so future audits can match exactly.
4. **Treat the GitHub Action and the underlying CLI as equivalent.** Many
   tools ship both an Action (e.g., `gitleaks/gitleaks-action`) and a CLI
   binary. Pick one approach for the workflow you generate, but mention the
   alternative in a YAML comment so an auditor can recognise either pattern,
   e.g. `# Equivalent CLI: gitleaks detect --redact --log-opts="..."`.
5. **Make job ordering explicit with `needs:`.** When one job depends on the
   output of another (lint must pass before tests, build must complete before
   deploy, format-check must run before auto-version-bump), declare the
   dependency with `needs: [<job>]`. Do not rely on accidental ordering from
   alphabetical job names.
6. **Provide a local preflight path.** Any tool that runs in CI should also be
   runnable locally before pushing. Add or reference a script under `scripts/`
   (e.g., `scripts/preflight.sh`, `scripts/check-codespell.sh`) that
   contributors can run on their workstation. Mention the preflight path in a
   YAML comment near the relevant step so reviewers can find it.
7. **Curate noisy linters with project-specific ignore lists.** Tools such as
   `codespell`, `jscpd`, and `markdownlint` produce false positives on
   domain-specific terminology (product names, acronyms, generated files).
   Commit an ignore list alongside the workflow (e.g.,
   `.codespell-ignore-words.txt`, `.jscpd.json`) and reference it from the
   workflow step rather than passing flags inline. This keeps the noise
   suppression auditable in version control.
8. **Auto-format and auto-version PR jobs must be guarded.** Jobs that commit
   back to a PR branch (formatter normalisation, version bumps) must:
   - Skip when the PR is from a fork (`if: github.event.pull_request.head.repo.full_name == github.repository`).
   - Use a token with explicit `contents: write, pull-requests: write`
     permissions, scoped only to the job that needs them.
   - Detect and skip when there is nothing to change (no formatting diff, or
     the version was already bumped on this PR) so the job is idempotent.

### Security Workflows

- Use CodeQL, Dependabot, or equivalent language-appropriate scanners.
- Schedule security scans (e.g., weekly via `schedule` cron) in addition to
  PR-triggered runs.
- Set `permissions: security-events: write` where needed for SARIF uploads.
- Apply the *CI Hardening Defaults* — in particular SHA-pin third-party
  scanners, scope scans to the PR diff range where supported, and pin the
  underlying CLI binary version with a YAML comment recording the pin.

### Quality Workflows

- Include linting, formatting, and type checking appropriate to the detected
  languages.
- Run on `pull_request` events targeting the default branch.
- Use caching (e.g., `actions/cache`) to speed up repeated runs.
- Apply the *CI Hardening Defaults* — make job ordering explicit with
  `needs:`, provide a local preflight script for every linter, and commit a
  curated ignore list alongside any noisy linter (codespell, jscpd, etc.).
