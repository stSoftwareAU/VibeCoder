## Instructions

Generate GitHub Actions workflow YAML for each missing workflow listed above.
Follow these guidelines:

### General Requirements

1. **Adapt to the repository context** — use the detected languages and default
   branch name to configure triggers, paths, and tool versions correctly.
2. **Trigger on relevant events only** — use `pull_request` for quality checks,
   `schedule` for periodic security scans, and `push` to the default branch
   where appropriate. Avoid overly broad triggers.
3. **Use the default branch name** — reference `{{DEFAULT_BRANCH}}` in branch
   filters rather than hard-coding `main` or `master`.
4. **Avoid conflicts** — check the existing workflows summary above and ensure
   generated workflows do not duplicate checks already in place.
5. **Group related checks** — where sensible, combine related checks into a
   single workflow file (e.g., lint + format in one quality workflow) to
   minimise CI overhead. Do not force unrelated checks together.
6. **Include clear comments** — add YAML comments explaining each step so
   maintainers understand the purpose without reading external documentation.
7. **Follow best practices** — use pinned action versions (e.g.,
   `actions/checkout@v4`), set appropriate timeouts, and use least-privilege
   permissions via the `permissions` key.
8. **Use Australian English** in all comments and descriptions (e.g., behaviour,
   colour, organisation, analyse, minimise).

### Security Workflows

- Use CodeQL, Dependabot, or equivalent language-appropriate scanners.
- Schedule security scans (e.g., weekly via `schedule` cron) in addition to
  PR-triggered runs.
- Set `permissions: security-events: write` where needed for SARIF uploads.

### Quality Workflows

- Include linting, formatting, and type checking appropriate to the detected
  languages.
- Run on `pull_request` events targeting the default branch.
- Use caching (e.g., `actions/cache`) to speed up repeated runs.
