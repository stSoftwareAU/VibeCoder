## General Coding Principles
Follow these principles where applicable:
- KISS: Favour simplicity; avoid unnecessary complexity.
- DRY: Avoid code duplication; maintain a single source of truth.
- Boy Scout Rule: Leave the code cleaner than you found it.
- Prefer smaller files: Favour many smaller, focused source files over large monolithic ones to follow the Single Responsibility Principle.
- IMPORTANT: Use Australian English spelling for all code, comments, and documentation (e.g., colour, behaviour, organisation, favour, metre, centre).

## Unit Tests vs Benchmarks
- **Unit tests are for functionality testing only**: Verify that code produces correct results, not how fast it runs. Do not validate performance in unit tests.
- **Benchmarks are for performance testing**: Use dedicated benchmarks to measure and compare execution time. Benchmarks are expected to take time.
- **Why this matters**: Unit tests run in parallel with other tests, making performance measurements unreliable. You will never get consistent timing results from unit tests.
- **IMPORTANT**: Do not reduce iteration counts to make "performance tests" faster in unit tests. If you need to confirm performance, create proper benchmarks and include benchmark results in the PR summary.

## Performance Task Workflow
For performance-related tasks, you MUST:
1. **Create benchmarks first**: Before making changes, create benchmark scripts that measure the current (baseline) performance.
2. **Implement the proposed change**: Make the performance improvement.
3. **Run benchmarks again**: Measure the new performance with the same benchmark scripts.
4. **Compare results**: Only if there is a demonstrated improvement, include the benchmark results in the PR.
5. **No gain = close the issue**: If benchmarks show no meaningful improvement (or worse performance), do NOT raise a PR. Instead, close the issue as "wontfix" with:
   - The benchmark results showing no gain
   - A brief explanation of what was tried
   - A "negative-result" label if available
   - A comment noting that a negative result is still valuable learning

A negative result is a result. Do not overcomplicate code for no good reason.

## Testing Best Practices
Every test must exercise real code: source a module, call a function with test data, and assert on results, exit codes, or side effects.
- Do NOT write tests that grep source files for patterns, inspect function bodies, check documentation for keywords, verify line counts, or assert that one function calls another. These are not real tests — they test implementation details and break on any refactor.
- Do NOT use `extract_function ... | grep` or `grep -qE '^function_name\(\)' "$FILE"` patterns.
- If a function requires external services (e.g., GitHub API) to test, skip it rather than faking a test with grep.
