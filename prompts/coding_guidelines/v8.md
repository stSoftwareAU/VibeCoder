## Token Economy (Issue #1409)
Claude Opus 4.7 uses an updated tokeniser that produces roughly 1.0–1.35× more tokens than earlier models for the same input. This prompt is injected into every session, so every word you save here saves tokens across every worker run.

- Write concise code comments — a single line explaining intent beats a paragraph restating the code.
- Keep commit messages, PR summaries, and response messages focused and short. Lead with the change; drop background the reviewer already knows.
- Produce short, direct responses for simple tasks. Scale length to genuine complexity, not to signal effort.
- Prefer one clear statement to the same instruction paraphrased three ways.

## General Coding Principles
- **KISS** — Favour simplicity. When choosing between two approaches, prefer the one with fewer moving parts and less indirection, even if it requires a few more lines of code.
- **DRY** — Avoid duplication; maintain a single source of truth.
- **Boy Scout Rule** — Leave the code cleaner than you found it.
- **Prefer smaller files** — Favour many smaller, focused source files over large monolithic ones. Three similar lines is better than a premature abstraction.
- **Use Australian English** — Apply to all code, comments, and documentation (colour, behaviour, organisation, favour, metre, centre).

## Secure Coding Principles (Issue #478)
Write secure code by design. Apply these principles to all generated code:

- **Validate and Sanitise Input**: Never trust user input. Validate type, length, and format server-side using allowlists, and sanitise to prevent injection attacks (SQLi, XSS).
- **Principle of Least Privilege**: Grant only the permissions necessary for each function.
- **Defence in Depth**: Layer security controls so that a single failure does not compromise the system.
- **Output Encoding**: Encode data sent to browsers or other interpreters to prevent attacks like XSS.
- **Secure Authentication and Authorisation**: Use strong authentication (e.g., multi-factor), proper session management, and enforce access control at every layer.
- **Avoid Security by Obscurity**: Rely on robust mechanisms (e.g., encryption), not hidden design.
- **Secure Error Handling and Logging**: Do not leak stack traces or architecture details to users. Log errors without exposing secrets.
- **Keep Dependencies Updated**: Scan and patch third-party libraries to mitigate known vulnerabilities.
- **Use Cryptography Safely**: Use industry-standard protocols (e.g., TLS) for data in transit and at rest. Never roll your own.
- **Security by Design**: Consider threat models and attack surfaces during design, not as an afterthought.
- **Code Analysis and Review**: Use SAST/DAST scanners and manual review to catch vulnerabilities early.

## Test Execution Best Practices (Issue #574)

### Cypress — Disable Video Recording
Always run Cypress with video recording disabled. Recording adds CPU, disk, and time overhead and produces `.mp4` files that are never used for PR evidence — Playwright MCP is the source of truth for screenshots.

- **Pass the flag**: `npx cypress run --config video=false`
- **Or set it in config**: `video: false` in the Cypress config file.

## Non-Interactive Test Execution
The Vibe Coder runs on unattended machines with no terminal. Redirect stdin from `/dev/null` for every test, quality check, or build command that could prompt for input:

```bash
./quality.sh < /dev/null
npm test < /dev/null
npx cypress run --config video=false < /dev/null
make check < /dev/null
```

A tool that unexpectedly reads from stdin will hang the worker indefinitely. Redirecting stdin makes it fail fast.

## Safe E2E Test Execution (Issue #575)

Full E2E suites can take 30+ minutes and cause stuck workers. Prevent hangs with targeted runs and timeouts.

### Targeted Test Execution
Run only the test files relevant to your changes:

- **Cypress** — use `--spec`:
  ```bash
  npx cypress run --spec "cypress/e2e/specific-test.cy.ts" --config video=false
  ```
- **Playwright** — pass the test file directly:
  ```bash
  npx playwright test specific-test.spec.ts
  ```

### Test Timeout Protection
Wrap long-running test commands with `$TIMEOUT_CMD` (set to `gtimeout` on macOS, `timeout` on Linux):

```bash
$TIMEOUT_CMD 900 npx cypress run --spec "cypress/e2e/specific-test.cy.ts" --config video=false
```

- Cap test execution at **10–15 minutes** (600–900 seconds).
- On timeout, report the timeout rather than retrying blindly.

### Avoid Running Full E2E Suites
Only run the full suite when the repository's quality command explicitly requires it. Otherwise prefer unit tests and targeted E2E runs. A full Cypress suite of 27+ specs can exceed 45 minutes and stall the worker.

## Unit Tests vs Benchmarks (Issue #603)

Unit tests verify correctness; benchmarks measure performance. Keep them separate.

- **Speed budget**: every unit test must finish within 120 seconds. BATS suites set `BATS_TEST_TIMEOUT=120`; Deno tests should complete within similar bounds. Most tests should finish in under 10 seconds.
- **Design for speed**: mock external calls, use small data sets, avoid sleep/polling loops.
- **Fix slow tests, do not raise the timeout**: a test that genuinely needs more than 30 seconds is likely testing too much or is really a benchmark.
- **Do not measure performance inside unit tests** — parallel execution makes timings unreliable. Use dedicated benchmarks when you need numbers.
- **Keep iteration counts honest** — do not shrink them to make a "performance test" fit inside a unit test. Write a proper benchmark and include the results in the PR summary.

## Performance Task Workflow (Issue #177)
For performance-related tasks:

1. **Create benchmarks first** — measure the baseline before changing code.
2. **Implement the change**.
3. **Run benchmarks again** — measure with the same scripts.
4. **Compare results** — include the numbers in the PR only if the change demonstrably improves them.
5. **No gain = close the issue** — if there is no meaningful improvement, close the issue as `wontfix` with:
   - The benchmark results showing no gain
   - A brief explanation of what was tried
   - A `negative-result` label if available
   - A note that the negative result is still valuable learning

A negative result is a result. Do not overcomplicate code for no good reason.

## Commit Safety
Never commit files that contain secrets or sensitive configuration. Before committing, verify none of these are staged:

- `.config*.json` files (may contain API keys or tokens)
- `*.secret.json` files (explicitly marked secret files)
- `.github/workflows/*.yml` or `.yaml` files (pushing requires the `workflow` OAuth scope the worker does not have — push will fail)

If one is staged by accident, remove it with `git reset HEAD <file>` before committing.

## Cross-Platform Bash Compatibility
This project uses `set -euo pipefail` and must run on **macOS (bash 3.2)**, **Ubuntu**, and **AWS Linux**.

- **Empty arrays under `set -u`**: bash 3.2 treats `${arr[@]}` on an empty array as an unbound variable error. Use the safe pattern `${arr[@]+"${arr[@]}"}`, or guard access with `if [[ ${#arr[@]} -gt 0 ]]; then`.
- **`timeout` command**: macOS has no native `timeout`. Use `$TIMEOUT_CMD` (resolved to `gtimeout` on macOS by `check_dependencies()`).
- **GNU vs BSD tools**: prefer POSIX-compatible flags. Document the dependency when GNU-specific flags are needed.

## Testing Best Practices
Every test must exercise real code: source a module, call a function with test data, and assert on results, exit codes, or side effects.

**Good** — calls a real function and asserts on the result:
```typescript
Deno.test("loadConfig - parses repos from JSON", async () => {
  await Deno.writeTextFile(path, JSON.stringify({ repos: ["org/repo1"] }));
  const config = await loadConfig(path);
  assertEquals(config.repos[0], "org/repo1");
});
```

**Avoid tests that inspect source text rather than behaviour** — they verify nothing useful and break on any refactor. Specifically, do not:

- Grep source files for function names, keywords, or line counts.
- Use `extract_function ... | grep` or `grep -qE '^function_name\(\)' "$FILE"`.
- Assert that one function "calls" another by inspecting its body.

If a function needs an external service (e.g., the GitHub API) to test, skip it rather than faking a test with grep.
