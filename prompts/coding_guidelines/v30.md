## General Coding Principles

- **KISS** — Favour simplicity. When choosing between two approaches, prefer the
  one with fewer moving parts and less indirection, even if it requires a few
  more lines of code.
- **DRY** — Avoid duplication; maintain a single source of truth.
- **Boy Scout Rule** — Leave the code cleaner than you found it.
- **Prefer smaller files** — Favour many smaller, focused source files over
  large monolithic ones. Three similar lines is better than a premature
  abstraction.
- **Use Australian English** — Apply to all code, comments, and documentation
  (colour, behaviour, organisation, favour, metre, centre).

## Never Fail Silently — Fail Loud

Generated code must never fail silently. If an operation fails, it must **fail
loud**: surface the fault immediately rather than swallowing it into a green
result. A silent failure looked green and ran broken for weeks in the FLEET
Discovery outage — a helper deleted in a PR was still `source`d, the
missing-`source` exit 127 was reconciled as success because no explicit failure
marker was present, and the fault went unnoticed. Attack that class at the root:
a fault must never be masked as success.

- **Surface every failure.** When an operation fails, exit non-zero, throw with
  context, or emit a clear failure marker. Do not let a fault return quietly.
- **Do not swallow errors.** Never catch-and-ignore an exception or discard a
  non-zero exit code. If you catch, either handle it meaningfully or re-raise
  with context — an empty `catch {}` that hides the error is forbidden.
- **Absence of a success marker is not success.** Do not treat "no explicit
  failure" as "passed", and do not treat an unhandled non-zero exit as benign. A
  result is only successful when success is positively confirmed.
- **No silent fallback that masks a fault.** A missing `source` target, a
  skipped stage, an empty result standing in for real data, or a default value
  papering over a failed fetch must not be reported as a clean outcome.
- **Prefer loud, early failure.** Fail fast at the point of the fault rather
  than continuing in a degraded or partial state that hides the problem
  downstream.

## Don't regress Deno repos to Node.js

A repo is a **Deno repo** if any of `deno.json`, `deno.jsonc`, or `deno.lock`
exist at the repo root. Treat the repo as Deno even when `package.json` is also
present — mixed repos are still Deno.

**In a Deno repo, never introduce Node-only tooling, dependencies, or
configuration.** Specifically, do not add or grow any of:

- `package.json`, `package-lock.json`, `pnpm-lock.yaml`, `yarn.lock`,
  `node_modules/`, `.nvmrc`.
- A `tsconfig.json` that overrides Deno's compiler options.
- Node-specific bundlers (Webpack, Vite, esbuild) where the repo already uses
  Deno's bundler.
- CI workflow steps that invoke `npm`, `pnpm`, `yarn`, or `npx` where Deno's
  task runner / `deno run` / `deno test` would suffice.
- Node-only dev dependencies (Jest, Mocha, ESLint, Prettier) where the Deno
  equivalents (`deno test`, `deno lint`, `deno fmt`) already cover the need.

**If the requested change genuinely can only be done with Node tooling**, do not
introduce the Node tooling in this run. Apply the escape hatch:
open a follow-up issue capturing the analysis and what a Node-tooling solution
would look like, post one message referencing the follow-up issue with "out of
scope" / "follow-up issue" wording, and exit cleanly.

**Note avoided regressions in the PR summary.** When you deliberately picked a
Deno-native path over a Node one, add a one-line entry under a **Deno regression
avoided** heading in `docs/archive/pr-summaries/pr-summary-*.md` so reviewers
can see the worker actively chose Deno over Node.

**Carve-out — Node-only repos stay Node.** This rule is regression-prevention,
not migration. Repos with no Deno markers stay on Node, and pre-existing Node
files inside a Deno repo are not cleaned up by this rule — leave them alone
unless the issue explicitly asks for removal.

## Secure Coding Principles

Write secure code by design. Apply these principles to all generated code:

- **Validate and Sanitise Input**: Never trust user input. Validate type,
  length, and format server-side using allowlists, and sanitise to prevent
  injection attacks (SQLi, XSS).
- **Principle of Least Privilege**: Grant only the permissions necessary for
  each function.
- **Defence in Depth**: Layer security controls so that a single failure does
  not compromise the system.
- **Output Encoding**: Encode data sent to browsers or other interpreters to
  prevent attacks like XSS.
- **Secure Authentication and Authorisation**: Use strong authentication (e.g.,
  multi-factor), proper session management, and enforce access control at every
  layer.
- **Avoid Security by Obscurity**: Rely on robust mechanisms (e.g., encryption),
  not hidden design.
- **Secure Error Handling and Logging**: Do not leak stack traces or
  architecture details to users. Log errors without exposing secrets.
- **Keep Dependencies Updated**: Scan and patch third-party libraries to
  mitigate known vulnerabilities.
- **Use Cryptography Safely**: Use industry-standard protocols (e.g., TLS) for
  data in transit and at rest. Never roll your own.
- **Security by Design**: Consider threat models and attack surfaces during
  design, not as an afterthought.
- **Code Analysis and Review**: Use SAST/DAST scanners and manual review to
  catch vulnerabilities early.

## Pre-PR Security Self-Check

Before creating a PR, verify the following (add to the PR summary if the change
is non-trivial):

- [ ] **Input validation**: Every new function accepting external input
      validates type, length, and format before use.
- [ ] **Secrets**: No API keys, tokens, credentials, or `.config*.json` files
      are staged.
- [ ] **Injection surface**: New SQL, shell, filesystem, or HTTP calls use
      parameterised APIs or allowlists — no string concatenation of user input
      into commands or queries.
- [ ] **Output encoding**: Any value rendered in HTML, logs, or external
      protocols is encoded for the target sink.
- [ ] **Authentication/authorisation**: New endpoints or privileged operations
      enforce the same access control as adjacent code.
- [ ] **Error handling**: No stack traces, file paths, or internal state leaked
      to user-facing responses.
- [ ] **Dependencies**: Any new third-party dependency is pinned, came from a
      trusted source, and has been recently maintained.

## Non-Interactive Test Execution

The Vibe Coder runs on unattended machines with no terminal. Redirect stdin from
`/dev/null` for every test, quality check, or build command that could prompt
for input:

```bash
./quality.sh < /dev/null
npm test < /dev/null

make check < /dev/null
```

A tool that unexpectedly reads from stdin will hang the worker indefinitely.
Redirecting stdin makes it fail fast.

## Streaming Reads — Never Use Unbounded `tail -f`

`tail -f file | head -N` looks reasonable but **wedges the worker forever** when
the writer dies before the next write. `head` slurps `N` lines and exits; the
next `tail` write would receive SIGPIPE and the pipeline would close — but if
the writer crashed (e.g. `deno test` died with SIGTRAP) there is no next write,
so `tail -f` blocks on read forever, the parent shell waits on `tail`, the Bash
tool waits on the shell, and the worker waits on the Bash tool. Production saw a
17h 45m wedge from this exact pattern.

Use these patterns instead:

- **Finished file** (the common case — the process you wanted to inspect has
  already exited):
  ```bash
  tail -n 50 /tmp/run.log
  head -n 50 /tmp/run.log
  ```
- **Live stream you must follow** — bound the wait with the project timeout
  helper:
  ```bash
  $TIMEOUT_CMD 30 tail -f /tmp/run.log | head -50
  ```
  `$TIMEOUT_CMD` resolves to `gtimeout` on macOS and `timeout` on Linux.

**Never** write `tail -f … | head` (or any unbounded `tail -f`) in a Bash-tool
command. Reach for `tail -n N <file>` first; only fall back to a guarded
`tail -f` when you genuinely need to watch new bytes arrive.

Full E2E suites can take 30+ minutes and cause stuck workers. Prevent hangs with

Run only the test files relevant to your changes:

- **Cypress** — use `--spec`:
  ```bash

  ```

  ```bash

  ```

Wrap long-running test commands with `$TIMEOUT_CMD` (set to `gtimeout` on macOS,


Only run the full suite when the repository's quality command explicitly
requires it. Otherwise prefer unit tests and targeted E2E runs. A full Cypress
suite of 27+ specs can exceed 45 minutes and stall the worker.

## Unit Tests vs Benchmarks

Unit tests verify correctness; benchmarks measure performance. Keep them
separate.

- **Speed budget**: every unit test must finish within 120 seconds. BATS suites
  set `BATS_TEST_TIMEOUT=120`; Deno tests should complete within similar bounds.
  Most tests should finish in under 10 seconds.
- **Design for speed**: mock external calls, use small data sets, avoid
  sleep/polling loops.
- **Fix slow tests, do not raise the timeout**: a test that genuinely needs more
  than 30 seconds is likely testing too much or is really a benchmark.
- **Do not measure performance inside unit tests** — parallel execution makes
  timings unreliable. Use dedicated benchmarks when you need numbers.
- **Keep iteration counts honest** — do not shrink them to make a "performance
  test" fit inside a unit test. Write a proper benchmark and include the results
  in the PR summary.

## Performance Task Workflow

When an issue involves performance improvement, optimisation, or speed-up,
follow this workflow strictly. **Do not raise a PR unless a measurable
improvement is demonstrated.**

1. **Create benchmarks first** — write or identify benchmark scripts that
   measure the relevant metric. Run them and record the baseline numbers before
   changing any code.
2. **Implement the change**.
3. **Run benchmarks again** — use the same benchmark scripts from step 1. Record
   the after numbers.
4. **Compare results** — only proceed to raise a PR if the change demonstrably
   improves the measured metric. Include the before/after numbers in the PR
   summary.
5. **No gain = close the issue** — if there is no meaningful improvement, **do
   not create a PR**. Instead:
   - Post a comment on the issue with the benchmark results (before and after)
     showing no gain.
   - Include a brief explanation of what was tried and why it did not help.
   - Add the `negative-result` label to the issue.
   - Close the issue as `not planned`. A negative result is still valuable
     learning — record it clearly.

**Do not raise a PR for a performance task without before/after benchmark
evidence.** A PR with no demonstrated improvement wastes reviewer time and will
be closed.

## Human Escalation

Any time you apply the `needs-human` label — for any reason — you must on the
same run post a comment that (a) explains why you applied the label and (b)
tells the human exactly what to do next. The label and the comment must always
appear together; never apply one without the other. The list below covers the
canonical escalation flow, but the rule applies to every `needs-human`
application.

When you cannot complete a task autonomously — for example, it needs access to a
system only a human can reach, or depends on a decision only a human can make —
escalate by:

1. Add the `needs-human` label to the issue (create the label if it does not
   exist).
2. Post a comment on the issue explaining what you attempted, why you could not
   complete it, and exactly what a human needs to do next.
3. Stop work on the issue — do not loop retrying the same failure.

**Never self-apply these reserved workflow labels — the worker account is not on
the trusted-author allowlist, so any reserved label you add is silently stripped
by the `label_security` check. Applying them is wasted effort and
can confuse the workflow.** They are managed by trusted humans,
not by you. The canonical pickup-priority order is `top-priority` > `work-on` >
`low-priority` > `idle-task`; only `idle-task` is self-appliable by the Vibe
Coder.

- `top-priority`
- `work-on`
- `low-priority`
- `failed`, `failed-once`
- `refine-issue`, `planning`
- `question`
- `best-model`

Self-applying `question` is especially harmful: that label is how humans ask the
Vibe Coder a question, so adding it to your own work either triggers an
unintended question-answering run or — more commonly — is silently stripped by
`label_security` and the run is wasted. Never add `question` yourself.

Use `needs-human` — and only `needs-human` — when you need a human to take over.

## Internal `stSoftwareAU/*` dependency fixes — fix the root cause cross-repo

When a root cause lives in a **dependency** rather than the repo you are working
in, what you do depends on whether that dependency is _internal_ or _external_.
Reuse the existing classification (see **Dependency Bumps and Supply
Chain** below): a dependency whose source repo is under `stSoftwareAU/*` is
**internal**; everything else is **external**. extends that classification
from _bumping_ deps to _fixing their root causes_.

- **Internal `stSoftwareAU/*` dependency you can access → fix the root cause
  cross-repo, in this run. Do NOT defer it to a follow-up issue.** "Can access"
  means the `stSoftwareAU/*` repo is reachable — you can clone it and open a PR
  against it. Fix the bug in the dependency's own repo (raise a PR there)
  **and** bring that fix into the consuming repo in the same run, relying on the
  cross-repo capability. A follow-up issue for the fix itself is **not** an
  acceptable default.
- **Recurse to where the root cause actually lives.** This rule is general to
  _every_ internal `stSoftwareAU/*` dependency — no single dependency is special
  — and it follows transitive internal dependencies: if the root cause is in an
  internal dependency _of_ an internal dependency, fix it there.
- **Unreachable internal dependency → treat as external.** If an
  `stSoftwareAU/*` repo cannot be cloned, or you cannot open a PR against it,
  treat it as external for this decision; deferring via the escape hatch below
  is then legitimate.

Deferral via a follow-up issue + `needs-human` (the escape hatch below) is
acceptable **only** for:

1. **external** (non-`stSoftwareAU/*`) dependencies,
2. genuine **human-only decisions**, or
3. a cross-repo fix that is **genuinely too big for one run** — and even then
   you must at minimum open a **draft/WIP PR in the dependency's repo**; never
   punt the whole fix to an issue. "Too big for one run" is almost never a valid
   reason to _fully_ defer an internal-dependency fix.

### Release-gating after the dependency PR is open

Once you have opened a PR in an internal `stSoftwareAU/*` dependency's own repo,
two boundaries must hold before that fix reaches the **consuming** repo:

- **No auto-release.** You must **not** auto-merge or **publish** the dependency
  PR yourself, and you must **not** bump the consumer to a raw
  **commit/git-ref** or a **pre-release** to pull the fix in early. Releasing
  the fixed dependency is a human decision; the consuming repo is bumped to the
  released version through the ordinary dependency-bump flow once that
  release exists.
- **Human-gated release is the one legitimate deferral here.** The only reason
  to defer _after_ the dependency PR is open is that the consumer bump needs a
  **human to release** the fixed dependency first. Handle it with exactly
  **one** follow-up — reusing (not redefining) the search-before-file /
  one-follow-up dedup rule above — filed in **either** the **consuming** repo
  (where the bump lands) **or** the **dependency repo** (beside the PR),
  whichever is reachable, and you must **cross-link** that follow-up to the open
  dependency PR so the two stay traceable.

## Escape Hatch — Hand Off When Genuinely Out of Scope

Use this when the task is genuinely too large or out of scope to complete in
this run — a PR review comment requesting a multi-day change, a CI failure
caused by missing infrastructure, or an issue whose scope exploded after
refinement. Looping until the timeout produces nothing useful and starves other
work. It is the **narrowed** relief valve for the cases just listed
(external-dependency root causes, human-only decisions, or a cross-repo fix
genuinely too big for one run — which still requires a draft/WIP PR in the
dependency repo); it is **not** the default for an internal `stSoftwareAU/*`
dependency root cause you can access — fix that cross-repo per the section
above.

If after substantive analysis you cannot complete this task within budget, do
this **instead of looping**:

1. **Search before you file — at most one follow-up per root cause.** A single root cause must produce **at most one** follow-up issue,
   and never a duplicate of one that already exists. Before creating anything,
   search the repo the follow-up belongs in for an existing **open** issue on
   the same root cause, e.g.
   `gh issue list --repo <owner>/<repo> --search "<root-cause terms> in:title,body" --state open`.
   If a genuine match exists, **comment on / reference that issue** instead of
   opening a new one — do not file a duplicate. Never split a single root cause
   across multiple follow-ups. This applies regardless of which deferral branch
   you took (external dependency, human-only decision, or human-gated release)
   and regardless of which repo the follow-up lands in.
2. Open a single follow-up GitHub issue in the relevant repository capturing
   what you have learnt: the precise problem, what you investigated, what is
   blocking, and what a solution would look like. Use
   `gh issue create --repo <owner>/<repo> --title "..." --body "..."`. Skip this
   step when step 1 found an existing open match — reference that issue instead.
3. Post **one** message that:
   - Names the follow-up issue you filed or referenced (e.g.
     `stSoftwareAU/foo#NNN`).
   - Explains in two sentences why this could not be resolved in-line. Use the
     wording "out of scope" or "follow-up issue" so the worker recognises the
     hand-off.
   - Adds the `needs-human` label to the follow-up issue if a person should
     triage. Mention `needs-human` explicitly in the message.

   For PR feedback or CI fix work, write the message to `.pr_response_message`
   in the working directory — the worker posts it as the PR reply. For issue
   work, post the message as a comment on the current issue and close the issue
   with that comment.
4. Exit cleanly. Do not retry the original change.

**Do not invoke this lightly.** Make a serious attempt first. Use the escape
hatch only when continuing would be a worse outcome than handing the work off.

> **Reminder:** if you add `needs-human` to the follow-up issue, the universal
> rule from [Human Escalation](#human-escalation) applies — the label
> and a same-run explanation comment must always appear together.

## Commit Safety

Never stage or commit hidden files. A _hidden file_ is any path with a component
matching `.*` (e.g. `.env`, `.aws/credentials`, `.ssh/id_rsa`). Hidden files
routinely carry secrets — `.env`, API keys, OAuth tokens, SSH keys — and a
single committed secret triggers full credential rotation.

**Allowlist — the only hidden paths that may ever be staged:**

- `.gitignore`
- `.github/` (workflow YAML files)
- `.markdownlint-cli2.jsonc` (markdownlint config —)

**Always-forbidden patterns — never stage, never `git add -f`:**

- `.env`, `.env.*` (dotenv files)
- `.config.json`, `.config*.json` (worker config; may contain API tokens)
- `*.secret.json` (explicitly marked secret files)
- `.secrets/` (secret directories)
- `.aws/`, `.ssh/`, `.gnupg/`, `.netrc` (credential stores)
- Any other hidden file not on the allowlist above

**Rules:**

1. Before every commit, check the staged set with
   `git diff --cached --name-only` and confirm no hidden path is present except
   those on the allowlist.
2. If a hidden file is staged by accident, run `git reset HEAD <file>` before
   committing.
3. **Never use `git add -f`** to bypass `.gitignore`. The ignore rules exist to
   stop secret leaks — bypassing them is forbidden.
4. If a hidden file legitimately needs to be tracked, raise an issue first and
   get human approval before adding the path to the allowlist in
   `worker/deno/lib/gitignore_enforcer.ts`. Do not add ad-hoc re-allow rules
   during normal work.

**Defence in depth.** Two safeguards back this rule, but they are _not_ a
substitute for following it:

- The `.gitignore` enforcer (`worker/deno/lib/gitignore_enforcer.ts`,) writes the canonical allowlist into every monitored repo's `.gitignore`
  after each clone or update.
- The pre-commit safety gate blocks any commit that stages a
  forbidden hidden path.

Bypassing either safeguard (e.g. `git commit --no-verify`, `git add -f`) is
forbidden. If a safeguard is producing a false positive, fix the allowlist via
PR — do not bypass.

## Cross-Platform Bash Compatibility

This project uses `set -euo pipefail` and must run on **macOS (bash 3.2)**,
**Ubuntu**, and **AWS Linux**.

- **Empty arrays under `set -u`**: bash 3.2 treats `${arr[@]}` on an empty array
  as an unbound variable error. Use the safe pattern `${arr[@]+"${arr[@]}"}`, or
  guard access with `if [[ ${#arr[@]} -gt 0 ]]; then`.
- **`timeout` command**: macOS has no native `timeout`. Use `$TIMEOUT_CMD`
  (resolved to `gtimeout` on macOS by `check_dependencies()`).
- **GNU vs BSD tools**: prefer POSIX-compatible flags. Document the dependency
  when GNU-specific flags are needed.

## Testing Best Practices

Every test must exercise real code: source a module, call a function with test
data, and assert on results, exit codes, or side effects.

**Good** — calls a real function and asserts on the result:

```typescript
Deno.test("loadConfig - parses repos from JSON", async () => {
  await Deno.writeTextFile(path, JSON.stringify({ repos: ["org/repo1"] }));
  const config = await loadConfig(path);
  assertEquals(config.repos[0], "org/repo1");
});
```

**Avoid tests that inspect source text rather than behaviour** — they verify
nothing useful and break on any refactor. Specifically, do not:

- Grep source files for function names, keywords, or line counts.
- Use `extract_function ... | grep` or `grep -qE '^function_name\(\)' "$FILE"`.
- Assert that one function "calls" another by inspecting its body.

If a function needs an external service (e.g., the GitHub API) to test, skip it
rather than faking a test with grep.

## Test Coverage Expectations

Every new or modified public function MUST have tests covering:

- **Happy path** — the primary success case with realistic inputs.
- **Error path** — at least one failure mode (invalid input, missing resource,
  external error) with an assertion on the returned error.
- **Edge cases** — boundary conditions relevant to the function (empty input,
  zero, maximum size, unicode, etc.).

For bug fixes, add a regression test that fails against the unfixed code and
passes after the fix. State this linkage in the PR summary (e.g., "Added
`tests/foo_test.ts::handles_empty_input` which reproduces ").

## Dependency Bumps and Supply Chain

Default to the latest version of every dependency on every PR. Two defences
against supply-chain attacks apply:

**Internal vs external classification.** Deps whose source repo is under
`stSoftwareAU/*` are _internal_ — bump to the latest commit/release immediately,
no quarantine. All other deps (npm, cargo/crates.io, third-party GitHub Actions)
are _external_ — quarantine versions newer than `VIBE_BUMP_QUARANTINE_HOURS`
(default 24h) since publish. This classification governs the **non-Deno**
ecosystems (npm, cargo, GitHub Actions); Deno deps follow the native-tooling
rule below.

**Deno deps — bump via native `deno` minimum-age, never hand-rolled
quarantine.** In a Deno repo (any of `deno.json`, `deno.jsonc`, `deno.lock`
present), bump Deno deps with the Deno CLI's built-in minimum-age support and
honour the repo's `deno.json` `minimumDependencyAge` config — do **not** write
custom age-gating or quarantine code for Deno deps.

- Run `deno outdated --update --latest --minimum-dependency-age=24h` (or
  `deno update --minimum-dependency-age=24h`). The flag enforces the 24h floor
  for **external** Deno deps even when the repo's `deno.json` has no
  `minimumDependencyAge`; when the config is present, the CLI already honours
  it.
- The canonical `deno.json` shape (from) is the object form:

  ```json
  "minimumDependencyAge": {
    "age": "P1D",
    "exclude": ["jsr:@stsoftware/*", "npm:@stsoftware/*"]
  }
  ```

  `age: "P1D"` is the ISO-8601 one-day (24h) external floor; `"24 hours"` is
  rejected by `deno check`. The `exclude` globs give internal `stSoftwareAU`
  Deno deps (`jsr:@stsoftware/*`, `npm:@stsoftware/*`) **0h** quarantine so they
  update immediately. No `--unstable-*` flag is needed on Deno v2.x.
- Internal `@stsoftware/*` Deno deps update at **0h**; all other (external) Deno
  deps respect the **24h** floor.

**Audit gate.** After bumping, run the per-tool audit (`cargo audit`,
`npm audit --audit-level=high`, `deno check`, etc.). If the audit reports a new
vulnerability introduced by the bump, revert the bump and continue without it.

**Pin GitHub Actions to commit SHAs**, not version tags
(`uses: actions/checkout@<40-char SHA>` not `@v4`) — this is where the worst
supply-chain attacks have historically landed.

**The bump and the substantive change land in the same PR.** Reviewers see the
fully-built state. If a per-repo `bump-deps.sh` exists, the worker invokes it
