## General Coding Principles
Follow these principles where applicable:
- KISS: Favour simplicity; avoid unnecessary complexity.
- DRY: Avoid code duplication; maintain a single source of truth.
- Boy Scout Rule: Leave the code cleaner than you found it.
- Prefer smaller files: Favour many smaller, focused source files over large monolithic ones to follow the Single Responsibility Principle.
- IMPORTANT: Use Australian English spelling for all code, comments, and documentation (e.g., colour, behaviour, organisation, favour, metre, centre).

## Secure Coding Principles (Issue #478)
Write secure code by design. Apply these principles to all generated code:

- **Validate and Sanitise Input**: Never trust user input. Validate inputs for type, length, and format on the server side using allowlists, and sanitise them to prevent injection attacks (e.g., SQLi, XSS).
- **Principle of Least Privilege**: Limit user and system permissions to only what is necessary to perform a specific function, reducing potential damage from a breach.
- **Defence in Depth**: Employ multiple, layered security controls rather than relying on a single defence, ensuring that if one fails, others protect the system.
- **Output Encoding**: Encode data sent to browsers or other systems to prevent interpreter-based attacks like Cross-Site Scripting (XSS).
- **Secure Authentication and Authorisation**: Implement strong authentication (e.g., multi-factor) and proper session management. Verify user identity and enforce access controls at every layer.
- **Avoid Security by Obscurity**: Do not rely on hiding code or design details to keep systems safe. Use robust security mechanisms (e.g., encryption) rather than attempting to keep design secret.
- **Secure Error Handling and Logging**: Avoid displaying detailed system, debugging, or stack trace information to users. Log errors securely without leaking secrets or system architecture.
- **Keep Dependencies Updated**: Regularly scan and patch third-party libraries and components to mitigate known vulnerabilities.
- **Use Cryptography Safely**: Protect data in transit and at rest using strong, industry-standard encryption protocols (e.g., TLS/SSL). Never roll custom cryptographic algorithms.
- **Security by Design**: Integrate security into the design phase of the development lifecycle, not as an afterthought. Consider threat models and attack surfaces early.
- **Code Analysis and Review**: Use automated scanners (SAST/DAST) and manual code reviews to identify vulnerabilities early in the development process.

## Test Execution Best Practices (Issue #574)

### Cypress — Disable Video Recording
When running Cypress tests, **always disable video recording**. Video recording adds significant overhead (CPU, disk I/O, and time) and generates large `.mp4` files that are never needed for PR evidence. Use Playwright MCP for visual evidence instead.

- **Pass the flag**: Always use `--config video=false` when running Cypress:
  ```bash
  npx cypress run --config video=false
  ```
- **Or set it in config**: If modifying the Cypress configuration file, set `video: false`.
- **Why**: Cypress video recordings are not needed for PR evidence — the worker captures evidence via Playwright MCP screenshots. Disabling video avoids wasted CPU, disk space, and execution time.

## Non-Interactive Test Execution
The Vibe Coder runs on unattended machines with no terminal. **Always redirect stdin from `/dev/null`** when running tests, quality checks, build commands, or any command that might prompt for user input:

```bash
./quality.sh < /dev/null
npm test < /dev/null
npx cypress run --config video=false < /dev/null
make check < /dev/null
```

**Why**: If a test or tool unexpectedly reads from stdin (e.g., a confirmation prompt, an interactive installer, or a `read` call), the worker will hang indefinitely waiting for input that will never arrive. Redirecting stdin ensures these commands fail fast instead of blocking.

## Safe E2E Test Execution (Issue #575)

Full E2E test suites can take 30+ minutes and cause stuck workers. Follow these practices to prevent hangs.

### Targeted Test Execution
When running E2E tests, prefer running only the specific test files relevant to your changes rather than the full suite:

- **Cypress** — use the `--spec` flag to target specific test files:
  ```bash
  npx cypress run --spec "cypress/e2e/specific-test.cy.ts" --config video=false
  ```
  instead of `npx cypress run`

- **Playwright** — pass the specific test file directly:
  ```bash
  npx playwright test specific-test.spec.ts
  ```
  instead of `npx playwright test`

### Test Timeout Protection
Wrap long-running test commands with a timeout to cap execution time. Use `$TIMEOUT_CMD` for cross-platform compatibility (macOS uses `gtimeout`, Linux uses `timeout`):

```bash
$TIMEOUT_CMD 900 npx cypress run --spec "cypress/e2e/specific-test.cy.ts" --config video=false
```

- Cap test execution at **10–15 minutes** (600–900 seconds) maximum.
- If a test suite exceeds the timeout, report the timeout rather than hanging indefinitely.

### Avoid Running Full E2E Suites
Do **not** run the full E2E suite unless the quality command explicitly requires it:

- Prefer unit tests and targeted E2E tests for validating your changes.
- Only run the full suite if the repository's quality command (e.g., `npm test`, `make check`) explicitly includes it as a required step.
- If the full suite must run, cap execution time with `$TIMEOUT_CMD` and report partial results on timeout.

**Why**: A full Cypress suite of 27+ spec files can exceed 45 minutes, causing the worker to become stuck. Targeted tests and timeouts prevent this.

## Unit Test Timeout Policy (Issue #603)
**A unit test that takes longer than 120 seconds is a failure.** Unit tests must be fast — they are not benchmarks. All BATS tests run with `BATS_TEST_TIMEOUT=120` (2 minutes per test). Deno tests should complete within similar bounds.

- **Design tests for speed**: Mock external calls, use small data sets, avoid sleep/polling loops.
- **If a test is slow, fix the test**: Refactor it to be faster, not increase the timeout. Slow tests indicate a design problem.
- **The timeout has a safety margin**: 120 seconds is generous for a unit test. Most should complete in under 10 seconds. If a test genuinely needs more than 30 seconds, it is likely testing too much or is actually a benchmark.
- **This applies across all repositories**: Every BATS test suite must set `BATS_TEST_TIMEOUT` in `setup()` or the test helper. A test that hangs is worse than a test that fails — it blocks the entire worker.

## Unit Tests vs Benchmarks
- **Unit tests are for functionality testing only**: Verify that code produces correct results, not how fast it runs. Do not validate performance in unit tests.
- **Benchmarks are for performance testing**: Use dedicated benchmarks to measure and compare execution time. Benchmarks are expected to take time.
- **Why this matters**: Unit tests run in parallel with other tests, making performance measurements unreliable. You will never get consistent timing results from unit tests.
- **IMPORTANT**: Do not reduce iteration counts to make "performance tests" faster in unit tests. If you need to confirm performance, create proper benchmarks and include benchmark results in the PR summary.

## Performance Task Workflow (Issue #177)
For performance-related tasks, you MUST:
1. **Create benchmarks first**: Before making changes, create benchmark scripts that measure the current (baseline) performance.
2. **Implement the proposed change**: Make the performance improvement.
3. **Run benchmarks again**: Measure the new performance with the same benchmark scripts.
4. **Compare results**: Only if there is a demonstrated improvement, include the benchmark results in the PR.
5. **No gain = close the issue**: If benchmarks show no meaningful improvement (or worse performance), do NOT raise a PR. Instead, close the issue as "wontfix" with:
   - The benchmark results showing no gain
   - A brief explanation of what was tried
   - A "negative-result" label if available
   - A comment noting that a negative result is still valuable learning

A negative result is a result. Do not overcomplicate code for no good reason.

## Commit Safety
Never commit files that contain secrets or sensitive configuration. Before committing, verify that none of these patterns are staged:
- `.config*.json` files (configuration files that may contain API keys or tokens)
- `*.secret.json` files (explicitly marked secret files)
- `.github/workflows/*.yml` or `.yaml` files (pushing these requires the `workflow` OAuth scope which the worker does not have — this will cause push failures)

If you accidentally stage any of these files, unstage them with `git reset HEAD <file>` before committing.

## Cross-Platform Bash Compatibility
This project uses `set -euo pipefail` and must run on **macOS (bash 3.2)**, **Ubuntu**, and **AWS Linux**.

- **Empty arrays under `set -u`**: Bash 3.2 treats `${arr[@]}` on an empty array as an unbound variable error. Use the safe expansion pattern `${arr[@]+"${arr[@]}"}` when an array might be empty. Alternatively, guard access with a length check: `if [[ ${#arr[@]} -gt 0 ]]; then`.
- **`timeout` command**: macOS doesn't have `timeout` natively. Use `$TIMEOUT_CMD` (set to `gtimeout` on macOS by `check_dependencies()`).
- **GNU vs BSD tools**: Prefer POSIX-compatible flags. When GNU-specific flags are needed, document the dependency.

## Testing Best Practices
Every test must exercise real code: source a module, call a function with test data, and assert on results, exit codes, or side effects.
- Do NOT write tests that grep source files for patterns, inspect function bodies, check documentation for keywords, verify line counts, or assert that one function calls another. These are not real tests — they test implementation details and break on any refactor.
- Do NOT use `extract_function ... | grep` or `grep -qE '^function_name\(\)' "$FILE"` patterns.
- If a function requires external services (e.g., GitHub API) to test, skip it rather than faking a test with grep.
