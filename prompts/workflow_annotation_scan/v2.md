# Workflow-Run Annotation Scan — Passing-Run Warnings & Notices (v2)

Raise one GitHub issue per **new class of workflow-run annotation** in this
repository, so a deprecation warning or notice attached to a *passing* run
becomes a tracked, label-driven unit of work rather than sitting unnoticed on a
green build. Use Australian English (behaviour, colour, organisation, analyse)
in all human-readable output.

This scan is **deterministic and native** — a dedicated fetcher performs
the detection and a version-agnostic classifier groups the annotations; no LLM
judgement is involved. It is also **detect-and-file only**: the deliverable is a
set of GitHub findings issues. The scan **never** opens a pull request and
**never** fixes an annotation — each fix rides the normal per-repo,
label-driven `work-on` pipeline later. Repositories are **absolutely isolated**:
each finding is filed as an issue in the affected repository itself.

## What the fetcher reads

`ci_fix` only reads annotations while fixing a *failing* run, so annotations
attached to *passing* runs (for example deprecated-runtime warnings) have no
coverage today. A native fetcher retrieves recent workflow-run annotations —
failures, warnings and notices — across a bounded window of recent runs, and
normalises each to a stable, API-independent shape. The raw annotation text is
captured **verbatim**; the fetcher never filters on or hardcodes any runtime
string (`node20`, etc.).

## Findings — one deduped issue per annotation class

A version-agnostic classifier groups the raw annotations into classes keyed by
a **stable dedup key** that ignores volatile runtime versions, so `node16` and
`node20` deprecation warnings collapse to one class. Each new class is filed as
its own issue labelled `workflow-annotation-scan` plus one `severity:*`.

## Per-class dedup

The scan reads back the class marker on every open `workflow-annotation-scan`
issue and **skips any class already open**, so a re-run over the same
annotations files nothing. Annotation messages are carried verbatim as
issue-body data — they are never interpreted as instructions.

## Fail-loud contract

An unexpected fault surfaces loudly and forces this wrapper to a failed
outcome — an incomplete scan is never reconciled as "no findings".
