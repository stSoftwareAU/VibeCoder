# Stop three self-inflicted loops: a settled PR's streak, an unusable local ref, and a clone/prune livelock

Three failures GRQ-23 hit overnight. Each is a pair of components that are
individually right and jointly wrong, and each repeats every cycle for ever.

## Issue #411 — a PR branch that exists is reported as not existing

```
Failed to checkout branch 'issue-387-side-data-…': error: pathspec
'issue-387-side-data-…' did not match any file(s) known to git
```

PR #408 is **OPEN** and its branch is on origin (`7a61ca3`) — verified with
`gh pr view` and `git ls-remote`. Three consecutive cycles failed anyway.

`checkoutPrBranchAtRemoteHead` read `refs/heads/<branch>` with `rev-parse
--verify`, then ran `git checkout <branch>` as a **separate command**, then
`reset --hard`. That shape fails two ways:

- a ref that resolves but names an object the clone does not have — the
  `fatal: bad object` / `unable to read tree` shape, which the same clone
  logged the night before — fails the checkout **permanently**;
- between the two commands another lane sharing the clone can delete the
  branch, and the second command reports it as never having existed.

Now the ahead-check runs **first**, on the state as read, and a single
`checkout -B <branch> origin/<branch>` positions the branch for every case:
absent → created, stale → reset, corrupt → overwritten. The local ref is never
*read* to get there, so neither failure has anywhere to happen. This is the
same correction as Issue #356, one layer up.

**Nothing is discarded that was not already unreachable.** The Issue #211
refusal is untouched and still fires on unpushed commits — a test asserts the
commit is still on the branch after the refusal. The one case that skips the
ahead-check is a ref whose commit `cat-file -e` cannot read: there is no
reachable work to protect, and the ref cannot be read, only replaced.

## Issue #409 — an escalated streak that can never clear

Suppression (Issue #335) short-circuits the loop **before** the finished-PR
check Issue #386 added. A branch whose streak had already escalated therefore
never reached it — and nothing else clears a streak: only a successful update
does, and no update ever succeeds on a merged PR. The escalation issue stayed
open for ever describing work nobody could do.

#409 is exactly that: filed against PR #405's branch, which had merged and
whose branch origin no longer has. Note the irony — PR #405 *is* the Issue #386
fix, and it could not clear its own streak.

A settled PR is now recognised before suppression, clears its streak, and is
counted as `mergedCount`. A PR that is genuinely still open keeps its streak
and stays suppressed, unchanged.

**The underlying failure #409 describes was already fixed by #405** — verified
by reading the pre-check it added. What is fixed here is the residue that kept
the issue alive.

## Issue #410 — clone and prune chasing each other for ever

```
05:55:58  Cloning private-repo-6 repository...
06:01:52  removed disposable GRQ-health (0.0 GB, 0.0 days idle, disk-low) — 47165440 bytes
06:01:53  Cloning private-repo-6 repository...
06:06:26  removed disposable GRQ-health … 47165440 bytes
06:06:34  Cloning private-repo-6 repository...
06:10:43  removed disposable GRQ-health … 47165440 bytes
```

Byte-identical, every ~4.5 minutes, indefinitely. The reclaimer tiers the
health checkout disposable and removes it at `0.0 days idle` while below the
floor; `ensureFleetHealthRepo` sees an absent directory and clones it back.
Because the volume image only grows (#384), each lap added 47 MB the host could
never reclaim — the loop actively worsened the shortage it was reacting to.

The clone is the side that yields: fleet health is optional reporting, and a
host already declining work for want of disk has better uses for what it has
left. `ensureFleetHealthRepo` now consults the **same** floor the reclaimer
acts on — `df -kP` plus the same env-configurable floors — and defers the
clone, logging why.

Deliberately narrow:

- **only the clone** is gated; an existing checkout is still fetched and reset,
  because it costs no new disk and a low-disk host is exactly when an operator
  wants to hear from it;
- the dependency is **optional**, so any caller that does not supply it behaves
  exactly as before;
- an unreadable `df` counts as *not* low — a probe failure must never silently
  switch health reporting off.

The emergency reclaimer is untouched. Its `selectLargestFirst` tests pin that
age is deliberately ignored under disk pressure, and weakening that to break
this loop would have traded a real safeguard for a symptom.
